1. El Concepto de Paginación

La paginación permite que el espacio de direcciones físicas de un proceso sea no contiguo. Esto soluciona definitivamente el problema de la fragmentación externa, permitiendo al SO usar cada rincón libre de la RAM.

Páginas (Visión Lógica)

Bloques de tamaño fijo (ej: 4 KB) en los que se divide el programa del usuario. Es como el índice de un libro.

Marcos / Frames (Visión Física)

Bloques del mismo tamaño en los que se divide la memoria RAM real. Son las hojas de papel físicas donde se imprime el libro.

Ventaja Laboral

La paginación permite **Compartir Memoria**. Si 100 usuarios ejecutan el comando ls, el SO solo carga una vez las páginas de código en RAM y las mapea a los 100 procesos. Ahorro masivo de recursos.

2. La Tabla de Páginas (Page Table)

Es el mapa que usa la MMU para traducir una dirección virtual en una física. Contiene PTE (Page Table Entries) con bits de control vitales:

  • V (Valid): ¿Está esta página cargada en la RAM?
  • R/W/X: Permisos de protección (Lectura, Escritura, Ejecución).
  • D (Dirty): ¿Se modificó la página? Si es así, hay que guardarla en disco antes de borrarla.

3. El Acelerador: TLB (Translation Lookaside Buffer)

Consultar la tabla de páginas en RAM cada vez que la CPU quiere un dato es demasiado lento (~100 ciclos de reloj). La CPU tiene una caché ultra-rápida llamada TLB que guarda las últimas traducciones.

Huge Pages en Aplicaciones Intensivas en Memoria

Para aplicaciones que manejan Terabytes de RAM (ej: sistemas de procesamiento de datos, análisis científico, ML), una página de 4KB genera tablas de páginas gigantes que no caben en el TLB. Los ingenieros habilitan Huge Pages (2MB o 1GB) para reducir los "TLB Misses" y ganar hasta un 20% de rendimiento.

4. Segmentación: La Visión del Programador

Divide la memoria en bloques según su función lógica (Stack, Heap, Código). A diferencia de la paginación, los segmentos tienen tamaño variable.

Los sistemas modernos usan Segmentación Paginada: el programador ve segmentos lógicos, pero el SO los trocea en páginas físicas por debajo.

5. Comandos de Inspección Técnica

Forense en Linux (Bash)

# Ver tamaño de página base
getconf PAGESIZE

# Ver memoria compartida (Inter-process)
ipcs -m

# Ver estadísticas de HugePages
cat /proc/meminfo | grep Huge

# Ver mapa de memoria virtual
cat /proc/self/maps

Forense en Windows (PowerShell)

# Ver contadores de paginación
Get-Counter "\Memory\Pages/sec"

# Ver info de memoria compartida
Get-CimInstance Win32_PageFileUsage

# Ver uso de Huge Pages (Large Pages)
whoami /priv | Select-String "SeLockMemory"

6. Actividad Práctica: Paging a Fondo

Laboratorio: Análisis de Memoria Compartida

Objetivo: Identificar cómo el SO optimiza la RAM mediante el mapeo de páginas.

Tarea 1: El tamaño de página (Linux)

  1. Ejecute getconf PAGESIZE. El estándar es 4096 bytes.
  2. Calcule: Si su servicio web ocupa 24MB de RAM real, ¿cuántas páginas de 4KB está gestionando el kernel para ese proceso?

Tarea 2: El archivo de Paginación (Windows)

  1. Abra PowerShell. Ejecute: Get-WmiObject Win32_PageFileUsage | Select-Object Name, CurrentUsage.
  2. Identifique el archivo pagefile.sys. ¿Qué sucede si borra ese archivo? (Tip: No lo haga, investigue por qué es vital para el kernel).

Tarea 3: Mapa de Proceso Real

En Linux, ejecute cat /proc/self/maps. Observe las librerías .so (ej: libc.so). Verá que están mapeadas en varios procesos a la vez. Esa es la magia de la paginación: un solo bloque de RAM física sirve para todos.

Casos Reales: Paginación en el Centro de Datos

Caso 1: Memory Ballooning en Máquinas Virtuales

Escenario: Un servidor ESXi o Proxmox tiene 10 máquinas virtuales. El hypervisor necesita RAM para una VM crítica y se la "infla" a las otras VMs.

Tu análisis:

  1. ¿Cómo sabe el hypervisor qué páginas de RAM están vacías dentro de la VM?
  2. ¿Por qué el driver de ballooning engaña al SO invitado para que libere páginas?

Caso 2: Huge Pages en Procesamiento de Datos

Escenario: Una aplicación de procesamiento de datos de 128GB de RAM corre lenta. Al habilitar Huge Pages de 2MB, el rendimiento sube un 15%.

Explicación: Con páginas de 4KB, la tabla de páginas tenía 32 millones de entradas. Con 2MB, solo tiene 64,000 entradas, lo que reduce drásticamente los TLB Misses.

Simulación Visual: Traducción de Direcciones Virtuales a Físicas

Ejercicio paso a paso:

Datos del sistema:

  • Espacio de direcciones virtuales: 32 bits
  • Tamaño de página: 4 KB (2^12 bytes)
  • Bits para offset: 12 bits
  • Bits para número de página: 20 bits

Paso 1 - Separar la dirección:

Dirección Virtual: 0x00401A3F

Binario: 0000 0000 0100 0000 0001 | 1010 0011 1111
          └────── 20 bits ──────┘   └─12 bits─┘
              N° Página              Offset
              0x00401                 0xA3F

Paso 2 - Consultar tabla de páginas:

Tabla de Páginas:
┌──────────┬──────────┬───────┬───────┐
│  Página  │  Marco   │ Validez│ Bits  │
├──────────┼──────────┼───────┼───────┤
│  0x00401 │  0x2B    │   V   │  R/W  │
│  0x00402 │  0x15    │   V   │  R/W  │
│  0x00403 │    -     │   I   │   -   │  ← Page Fault!
└──────────┴──────────┴───────┴───────┘

Paso 3 - Construir dirección física:

Dirección Física = (Marco × Tamaño_Página) + Offset
                  = (0x2B × 4096) + 0xA3F
                  = 0x2B000 + 0xA3F
                  = 0x2BA3F

Cálculo Manual: Números de Página y Offset

Fórmulas:

Número de Página = floor(Dirección_Virtual / Tamaño_Página)
Offset = Dirección_Virtual % Tamaño_Página

Ejercicios:

Dirección VirtualTamaño PáginaN° PáginaOffset
0x0001A4F04 KB??
0x00B3C2104 KB??
0x7FFF80004 KB??
0x00005A5A4 KB??

Solución para el primero:

0x0001A4F0 = 107760 en decimal
N° Página = floor(107760 / 4096) = floor(26.308) = 26 = 0x1A
Offset = 107760 % 4096 = 2544 = 0x9F0

Caso Real: ¿Por qué 4KB es el Tamaño Estándar de Página?

Factores que determinaron el estándar de 4KB:

  1. Equilibrio TLB vs Fragmentación:
    • Páginas más grandes = Menos entradas en tabla = Mejor TLB hit rate
    • Pero: Mayor fragmentación interna (desperdicio de memoria)
    • 4KB fue el "punto dulce" encontrado empíricamente
  2. Hardware histórico:
    • Intel 80386 (1985) introdujo paginación con páginas de 4KB
    • Compatibilidad heredada durante décadas
  3. Trade-offs:
    • 4KB: Bueno para uso general, sistemas mixtos
    • 2MB (Huge Pages): Mejor para bases de datos, menos TLB misses
    • 1GB (Gigantic Pages): Para aplicaciones de memoria masiva (ML, Big Data)

Ejercicio de reflexión:

Una aplicación de procesamiento de datos usa 128GB de RAM.
Con páginas de 4KB:  128GB / 4KB = 33,554,432 entradas de página
Con páginas de 2MB:  128GB / 2MB = 65,536 entradas de página
Con páginas de 1GB:  128GB / 1GB = 128 entradas de página

TLB típico tiene 512 entradas.

Troubleshooting: Huge Pages en Bases de Datos

Problema común: Tu aplicación está configurada para usar Huge Pages pero no arranca o no usa la memoria esperada.

Diagnóstico en Linux:

# 1. Verificar soporte de Huge Pages
cat /proc/cpuinfo | grep -i pdpe1gb  # Soporte 1GB

# 2. Ver configuración actual
cat /proc/meminfo | grep -i huge

# 3. Verificar límites del usuario
ulimit -l  # Memoria lockable (KB)

# 4. Verificar uso por proceso
cat /proc/[PID]/smaps | grep -i huge

Configuración para Aplicaciones Intensivas:

# 1. Calcular cuántas Huge Pages necesitas
# Aplicación: memoria_compartida = 8GB
# Huge Page size = 2MB
# Necesitas: 8GB / 2MB = 4096 Huge Pages

# 2. Configurar kernel
sudo sysctl -w vm.nr_hugepages=4096

# 3. Hacer persistente
echo "vm.nr_hugepages=4096" >> /etc/sysctl.conf

# 4. Configurar la aplicación
huge_pages = on
memoria_compartida = 8GB

# 5. Configurar límites de usuario (/etc/security/limits.conf)
aplicacion soft memlock 8388608
aplicacion hard memlock 8388608

Verificación:

# Verificar que la aplicación está usando Huge Pages
cat /proc/[PID_APLICACION]/smaps | grep "AnonHugePages"
# Debería mostrar uso de AnonHugePages

# Verificar estadísticas
cat /proc/vmstat | grep -i thp  # Transparent Huge Pages

Problemas comunes:

  • ulimit insuficiente: El usuario no puede lockear memoria suficiente
  • Fragmentación: No hay bloques contiguos de 2MB disponibles
  • Transparent Huge Pages (THP): Puede causar latencia por compactación
