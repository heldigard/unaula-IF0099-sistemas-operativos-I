1. El Manual Técnico: Para el próximo ingeniero

Un ingeniero no solo construye; sabe explicar qué construyó para que otros puedan replicarlo o repararlo.

Estructura Sugerida:

  • Arquitectura Lógica: Diagrama de red y flujo de datos.
  • Matriz de Direccionamiento: IPs, Puertos y MACs.
  • Configuraciones de Kernel: Parámetros modificados en sysctl o Registro.
  • Seguridad: Políticas de hardening aplicadas.

2. Manual de Operación: Para el usuario final

Se enfoca en el "Cómo se usa". Es la guía rápida para que un operador de sistemas mantenga el servicio arriba.

  • Arranque y Parada: Comandos para iniciar Apache e IIS.
  • Monitoreo: Cómo leer la salida de los scripts de la Fase 2.
  • Troubleshooting Básico: Qué hacer si el sitio web muestra un error 500 o 503.

3. Markdown: El Estándar de la Documentación

Olvídese de Word. Los ingenieros modernos documentan en Markdown para que la documentación viva junto al código en el repositorio (GitHub/GitLab).

4. Diagramación de Infraestructura

Casos Reales: Documentación en el Mundo Real

Caso 1: El Servidor Sin Documentación

Escenario: Un administrador se retira de la empresa y deja un servidor con configuraciones personalizadas. El nuevo administrador no sabe qué hace cada script en /opt/ ni por qué hay reglas de firewall específicas.

Lección: Cada script debe tener un README en su misma carpeta explicando:

  • Qué hace el script
  • Con qué permisos se ejecuta
  • Con qué otros sistemas interactúa
  • Quién lo mantiene

Caso 2: El Diagrama de Red Desactualizado

Escenario: El diagrama de red muestra un servidor en 192.168.1.50 pero ese servidor fue migrado a 192.168.1.75 hace 6 meses. Un proveedor externo intenta conectarse y no puede.

Solución - GitOps para documentación:

# Usar Git para versionar la documentación
cd /repo/infraestructura
git pull origin main

# Editar diagrama.drawio
# Commit con mensaje descriptivo
git add .
git commit -m "Actualización: Servidor app migrado a 192.168.1.75"
git push origin main

Caso 3: El Manual de Operaciones Inutilizable

Escenario: El manual dice "Ejecute el script de restart.sh" pero nadie sabe dónde está, con qué usuario ejecutarlo, ni qué hace el script cuando falla.

Estructura profesional de un manual:

## Procedimiento: Reiniciar Servicio Web

### Ubicación del Script
`/opt/ucs/scripts/restart_apache.sh`

### Usuario Requerido
`sudo -u www-data` (nunca como root)

### Pasos
1. Verificar estado actual: `systemctl status apache2`
2. Ejecutar script: `bash /opt/ucs/scripts/restart_apache.sh`
3. Verificar puertos: `netstat -tlnp | grep :80`

### Qué Hacer Si Fallla
- Ver logs: `tail -50 /var/log/apache2/error.log`
- Verificar puertos ocupados: `lsof -i :80`
- Contactar al equipo de seguridad si hay errores de permisos

  • Code examples: Múltiples lenguajes (CLI, Python, Java).

Google Cloud Documentation:

  • Quickstarts: 5 minutos para "Hello World".
  • Conceptos: Explicaciones profundas antes de tutoriales.
  • Best practices: Secciones destacadas de recomendaciones.

Microsoft Docs:

  • Modular: Cada página es un "learning unit".
  • Interactive: Sandbox para probar código.
  • Version-aware: Selector de versión del producto.

  - admonition
  - toc:

# Servir localmente
mkdocs serve

# Construir sitio
mkdocs build

Extensiones útiles de Markdown:

  • Admonition: Cajas de notas, warnings, tips.
  • Code blocks: Sintaxis highlight.
  • Tables: Datos tabulares.
  • Emoji: Iconos visuales :warning: :rocket: :white_check_mark:.

Mejores Prácticas: Cómo Escribir Documentación que Sí Lean

✅ Hacer:

  • Escribir para el lector objetivo (novato vs experto).
  • Usar ejemplos concretos de comandos.
  • Incluir screenshots de resultados esperados.
  • Organizar por tareas, no por features.
  • Verificar que los comandos funcionan copiando y pegando.
  • Actualizar cuando cambia el sistema.
  • Usar lenguaje simple y directo.
  • Incluir "TL;DR" al inicio de secciones largas.

❌ Evitar:

  • Jerga técnica innecesaria.
  • Bloques de texto largos sin formato.
  • Suponer conocimiento previo no documentado.
  • Documentación desactualizada.
  • Duplicar información en múltiples lugares.
  • Documentar lo obvio.
  • Usar pronombres ambiguos ("esto", "eso").
  • Olvidar el contexto del "por qué".

💡 Principio Diátaxis: Organiza documentación en 4 tipos:

  1. Tutoriales: Aprendizaje guiado paso a paso.
  2. How-to guides: Resolver problemas específicos.
  3. Referencias: Información técnica precisa.
  4. Explicaciones: Entender conceptos y decisiones.

Checklist de Calidad de Documentación

Antes de entregar, verifica:

  • README.md tiene título, descripción, y requisitos claros
  • Todos los comandos fueron probados en una VM limpia
  • Diagramas están actualizados y en alta resolución
  • Tablas de configuración son completas (IPs, puertos, usuarios)
  • Troubleshooting cubre al menos 5 problemas comunes
  • No hay errores de ortografía ni gramática
  • Formato Markdown es válido (usar linter)
  • Enlaces externos funcionan correctamente
  • Imágenes tienen descripciones (alt text)
  • Documentación está versionada (fecha, versión, autor)
