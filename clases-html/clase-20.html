1. SRE: Site Reliability Engineering

La ingeniería de confiabilidad es la disciplina que aplica principios de ingeniería de software a problemas de operaciones de sistemas.

Métricas Clave (SLAs / SLIs)

  • Disponibilidad (Uptime): Porcentaje del tiempo que el servicio web está arriba.
  • Latencia: Tiempo de respuesta promedio de Apache/IIS.
  • Tasa de Errores: Porcentaje de peticiones que fallan (Error 500).

2. Pruebas de Estrés: Llevando el SO al Límite

¿Qué pasa con la RAM si llegan 1000 usuarios a la vez? ¿Cómo reacciona el kernel?

Herramientas Linux

  • stress-ng: Carga artificial de CPU y RAM.
  • Apache Benchmark (ab): Genera miles de peticiones HTTP.

Herramientas Windows

  • CPUSTRES: (Sysinternals) Controla la carga por hilo individual.
  • Performance Monitor: Graba el impacto en disco durante el pico.

3. QA del Sistema Operativo

Antes de la sustentación, debe validar la integridad de su infraestructura:

  1. Prueba de Reinicio (Cold Boot): ¿Suben los servicios automáticamente? ¿El RAID se monta solo?
  2. Prueba de Conectividad: ¿El Nodo Windows puede ver el portal de Linux? ¿Las IPs son estáticas?
  3. Prueba de Seguridad: ¿El puerto 22 está realmente bloqueado desde afuera?

5. Actividad Práctica: Simulacro de Desastres

Taller de Pre-Sustentación

Objetivo: Preparar el sistema para las preguntas de parrilla del docente.

Tarea 1: Stress Test (Linux)

  1. Instale stress-ng: sudo apt install stress-ng.
  2. Lanza carga de memoria: stress-ng --vm 2 --vm-bytes 1G --timeout 60s.
  3. Observe en htop cómo el SO gestiona la presión de RAM. ¿Se activó el Swap?

Tarea 2: HTTP Benchmark

  1. Desde Linux, ataque su servidor Windows: ab -n 1000 -c 10 http://[IP_WINDOWS]:8080/.
  2. Vea cuántas peticiones por segundo soporta su IIS virtualizado.

Tarea 3: QA Final Checklist

  • Verifique que /etc/fstab tiene el UUID correcto.
  • Verifique que las llaves SSH funcionan sin contraseña (Hardening).
  • Limpie archivos temporales y logs de prueba para entregar un sistema "limpio".

Entregable: Un video corto (máx 3 min) donde demuestre que tras reiniciar ambas VMs, los servidores web Apache e IIS están en línea sin intervención manual.

Casos Reales: SRE y QA en Producción

Caso 1: El Servidor que Caía a las 2 AM

Escenario: Un servidor de base de datos MySQL caía cada noche a las 2:00 AM exactamente. Los logs no mostraban errores. Era un job de backup que consumía toda la RAM.

Cómo se resolvió:

# Linux: Monitoreo con htop top
htop

# Ver consumo de memoria por proceso
ps aux --sort=-%mem | head -10

# Ver logs de cron
sudo tail -f /var/log/cron

# Crear alerta
grep "OOM" /var/log/syslog

Lección: Siempre programa trabajos pesados (backups) en horas de baja actividad y configura monitoreo de memoria.

Caso 2: IIS Muere tras Actualización de Windows

Escenario: Después de instalar actualizaciones de Windows Server, IIS no iniciaba. Error 503 en el sitio web.

Diagnóstico:

# Ver estado de IIS
Get-Service W3SVC

# Ver logs de error
Get-Content C:\Windows\System32\LogFiles\HTTPERR\*.log -Tail 50

# Ver eventos
Get-EventLog -LogName System -Source IIS* -Newest 20

Solución:

# Reiniciar IIS
iisreset

# Si persiste, verificar Application Pools
Get-WebAppPoolState

# Reconstruir configuración si es necesario
aspnet_regiis -ua
aspnet_regiis -i

Caso 3: La Prueba de Carga que Derribó el Prod

Escenario: Un tester corrió Apache Benchmark contra el servidor de producción (no de prueba) pensando que era QA. El servidor se sobrecargó.

Prevención:

  • Entornos separados: NUNCA ejecutes pruebas de estrés en producción.
  • Rate limiting: Configura límites en Apache para prevenir DDoS accidentales.
  • Alertas: Configura alertas cuando CPU > 90% o memoria > 85%.

Ejercicios de Estimación: Cálculo de SLAs, SLOs, SLIs para el Proyecto UCS

Definiciones Clave:

  • SLA (Service Level Agreement): Compromiso con el cliente/usuario. Ej: "99.9% de uptime mensual".
  • SLO (Service Level Objective): Meta interna del equipo. Ej: "99.95% de uptime" (más estricto que SLA).
  • SLI (Service Level Indicator): Métrica medible. Ej: "Tiempo de respuesta del servidor web < 200ms".

Ejercicio 1: Definir SLIs para UCS

Componente SLI Método de Medición
Servidor Web Apache Latencia < 200ms (p95) Apache Bench: ab -n 1000 -c 10
Disponibilidad Uptime > 99.5% Monitoreo con ping/script
Share Samba Tiempo de respuesta < 500ms smbclient time command
Tasa de Error HTTP 5xx < 0.1% Logs de Apache/IIS

Ejercicio 2: Calcular Presupuesto de Error

# Presupuesto de Error = 1 - SLO
# Ejemplo: SLO de 99.9% = 0.1% de error permitido

# Cálculo para UCS con SLO 99.5%:
- Tiempo mensual: 30 días × 24 horas × 60 minutos = 43,200 minutos
- Presupuesto de error: 0.5% de 43,200 = 216 minutos/mes
- Equivalente a: 3.6 horas de downtime permitido al mes

# Distribución del presupuesto:
- Mantenimiento planificado: 120 minutos
- Fallos inesperados: 60 minutos
- Buffer de emergencia: 36 minutos

# Si excedemos el presupuesto:
- Priorizar estabilidad sobre nuevas features
- Realizar post-mortem
- Implementar mejoras preventivas

Ejercicio 3: Definir Alertas

# Sistema de alertas simple con scripts

#!/bin/bash
# monitor-ucs.sh

# 1. Verificar Apache
if ! systemctl is-active --quiet apache2; then
    echo "[ALERTA] Apache caído - $(date)" | mail -s "UCS Alert" admin@ucs.local
fi

# 2. Verificar latencia
LATENCIA=$(curl -o /dev/null -s -w "%{time_total}" http://localhost)
if (( $(echo "$LATENCIA > 0.5" | bc -l) )); then
    echo "[ALERTA] Latencia alta: ${LATENCIA}s" | mail -s "UCS Performance" admin@ucs.local
fi

# 3. Verificar espacio en disco
USO_DISCO=$(df / | tail -1 | awk '{print $5}' | sed 's/%//')
if [ $USO_DISCO -gt 85 ]; then
    echo "[ALERTA] Disco al ${USO_DISCO}%" | mail -s "UCS Storage" admin@ucs.local
fi

# Agregar a cron cada 5 minutos
# */5 * * * * /opt/ucs/monitor-ucs.sh

Casos de Estudio: Post-mortems Famosos (GitHub, AWS, Google) - Qué Aprender

Caso 1: GitHub - Outage de 24 horas (2018)

Qué pasó: Fallo de orchestrator (MySQL) causó pérdida de datos de 43 segundos.

Lecciones:

  • ✅ Simular escenarios de failover antes de producción.
  • ✅ Tener planes de rollback claros.
  • ✅ Comunicación transparente con usuarios durante incidentes.

Ver reporte completo: github.com/blog/github-outage-2018

Caso 2: AWS S3 - Outage de 4 horas (2017)

Qué pasó: Error humano en comando de mantenimiento desactivó más servidores de lo previsto.

Lecciones:

  • ✅ Validación de comandos destructivos con "dry-run".
  • ✅ Rate limiting en operaciones de mantenimiento.
  • ✅ Separación de ambientes críticos.
  • ✅ Dashboards de status independientes de la infraestructura afectada.

Caso 3: Google Cloud - Packet Loss (2019)

Qué pasó: Cambio de configuración de red causó pérdida de paquetes del 5%.

Lecciones:

  • ✅ Rollback automático si métricas degradan.
  • ✅ Testing en producción con tráfico canario (pequeño %).
  • ✅ Documentar dependencias entre servicios.

Estructura de un Post-mortem Profesional:

  1. Resumen ejecutivo: Qué pasó, impacto, duración.
  2. Timeline: Minuto a minuto del incidente.
  3. Root cause: Causa raíz identificada (5 Whys).
  4. Impacto: Usuarios afectados, datos perdidos, costo.
  5. Detección: Cómo se detectó el problema.
  6. Respuesta: Acciones tomadas para mitigar.
  7. Lecciones aprendidas: Qué funcionó, qué no.
  8. Acciones correctivas: Tareas específicas con owners y deadlines.

⚠️ Cultura de Blameless: El post-mortem busca mejorar procesos, no culpar personas.

Preparación para Sustentación

1. Guía de Oratoria Técnica

  • Estructura: 1) Hook (30 seg), 2) Problema (1 min), 3) Solución (2 min), 4) Demo (10 min), 5) Cierre (1 min).
  • Regla del 10-20-30: Máximo 10 slides, 20 minutos, fuente mínimo 30 puntos.
  • Lenguaje corporal: Postura abierta, contacto visual, gestos naturales.
  • Voz: Volumen adecuado, pausas estratégicas, variación de tono.
  • Práctica: Grabarse, presentar frente a espejo, ensayar con amigos.

2. Tips para Demostraciones en Vivo

Antes de la demo:

  • ☐ VMs encendidas y probadas
  • ☐ Plan B si algo falla (screenshots, videos)
  • ☐ Comandos copiados en notepad (no tipear en vivo)
  • ☐ Cronómetro para no exceder tiempo

Durante la demo:

  • ☐ Narrar lo que estás haciendo
  • ☐ Mostrar solo lo importante (no detalles técnicos aburridos)
  • ☐ Si hay error, mantener calma: "Veamos esto como oportunidad de troubleshooting"

3. Preguntas Frecuentes y Cómo Responderlas

Pregunta Cómo responder
"¿Por qué eligieron X sobre Y?" Mencionar requisitos, trade-offs evaluados, y decisión fundamentada.
"¿Qué harían diferente?" Mostrar autocrítica constructiva y aprendizajes.
"¿Cómo escalaría esto?" Mencionar load balancers, clusters, CDN, etc.
"¿Qué pasa si falla X?" Describir redundancia, backups, y plan de recuperación.
"¿Cuánto costaría en producción?" Tener estimados de AWS/Azure: VMs, storage, bandwidth.
