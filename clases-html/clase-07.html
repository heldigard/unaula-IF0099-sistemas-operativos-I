Proceso vs Thread (Hilo)

Un hilo (thread) es la unidad básica de ejecución dentro de un proceso

Comparación Proceso vs Thread

Característica Proceso Thread
Espacio de direcciones Independiente y aislado Compartido entre threads
Recursos Propios (archivos, memoria) Compartidos del proceso
Comunicación IPC complejo (pipes, shared memory) Directa (memoria compartida)
Contexto Pesado ( PCB completo) Ligero (registros, stack)
Cambio de contexto Lento (miles de ciclos) Rápido (cientos de ciclos)
Creación Lenta y costosa Rápida y económica

Ejemplo de múltiples threads en un proceso:

┌─────────────────────────────────────────────────────┐
│                   PROCESO (ej. Chrome)               │
│  Espacio de memoria: código, datos, heap compartido │
├─────────────┬─────────────┬─────────────┬─────────────┤
│  Thread 1   │  Thread 2   │  Thread 3   │  Thread 4   │
│  (Pestaña)  │  (Pestaña)  │  (Renderer) │  (Network)  │
├─────────────┼─────────────┼─────────────┼─────────────┤
│ Stack       │ Stack       │ Stack       │ Stack       │
│ independiente│ independiente│ independiente│ independiente│
├─────────────┴─────────────┴─────────────┴─────────────┤
│   Código, datos, archivos, sockets (compartidos)     │
└─────────────────────────────────────────────────────┘

Ventajas de usar threads:

  • Responsividad: UI permanece activa mientras se procesa en background
  • Economía: Menos recursos que crear procesos
  • Compartición: Fácil acceso a recursos compartidos
  • Paralelismo: Aprovechar múltiples CPUs

Sincronización de Threads

El problema: Cuando múltiples threads acceden a datos compartidos simultáneamente

Condición de Carrera (Race Condition)

Tiempo    Thread A              Memoria          Thread B
────────────────────────────────────────────────────────────────
  t1      lee saldo (1000)      [saldo=1000]
  t2                            [saldo=1000]     lee saldo (1000)
  t3      suma 100 (local=1100)
  t4                                             resta 50 (local=950)
  t5      escribe 1100          [saldo=1100]
  t6                            [saldo=950]      escribe 950
────────────────────────────────────────────────────────────────
                                 RESULTADO: $950 (¡incorrecto!)
Una condición de carrera ocurre cuando el resultado depende del orden de ejecución

Mutex (Mutual Exclusion)

Mutex es un lock que permite solo un thread a la vez en una sección crítica

Características del Mutex:

  • Propiedad: El thread que lo adquiere es el único que puede liberarlo
  • Exclusión: Solo un thread puede tener el mutex a la vez
  • Bloqueo: Si el mutex está ocupado, el thread espera
  • Sección crítica: Código que accede a recursos compartidos

Operaciones básicas:

┌─────────────────────────────────────────────────┐
│  Thread 1                │  Thread 2          │
├─────────────────────────────────────────────────┤
│  lock(mutex)             │                    │
│  // Sección crítica      │  lock(mutex)       │
│  modificar_compartido()  │  // Espera...      │
│  unlock(mutex)           │  // Espera...      │
│                          │  // Se libera...   │
│                          │  // Sección crítica│
│                          │  modificar_compartido()│
│                          │  unlock(mutex)     │
└─────────────────────────────────────────────────┘

Ejemplo conceptual (sin código):

Escenario: Dos cajeros acceden a la misma cuenta bancaria

  • Sin mutex: Ambos leen al mismo tiempo → resultado inconsistente
  • Con mutex: Uno accede primero, termina, luego el otro → resultado correcto

Semáforos

Un semáforo es un contador entero que controla el acceso a recursos

Tipos de Semáforos:

Semáforo Binario (0 o 1)

  • Similar a un mutex
  • Un solo recurso disponible
  • Usado para exclusión mutua
  • S = 1: recurso libre
  • S = 0: recurso ocupado
wait(S):  // Adquirir
  while S == 0;  // Espera si está ocupado
  S = 0;

signal(S):  // Liberar
  S = 1;

Semáforo Contador (0 a N)

  • N recursos idénticos
  • Hasta N threads pueden acceder
  • Usado para pool de recursos
  • S = N: N recursos libres
  • S = 0: todos ocupados
wait(S):  // Adquirir
  while S == 0;  // Espera si no hay recursos
  S = S - 1;

signal(S):  // Liberar
  S = S + 1;

Ejemplo de uso - Pool de conexiones:

Semáforo con valor inicial = 5 (5 conexiones disponibles)

  • Thread A hace wait(): semáforo = 4
  • Thread B hace wait(): semáforo = 3
  • Thread C hace wait(): semáforo = 2
  • Thread A termina y hace signal(): semáforo = 3
  • Thread D hace wait(): semáforo = 2

Monitores

Un monitor es una estructura de alto nivel que encapsula datos y métodos de sincronización

Características de los Monitores:

  • Encapsulamiento: Datos y métodos sincronizados en una unidad
  • Exclusión automática: Solo un thread puede estar activo en el monitor
  • Colas de espera: Threads esperan en variables de condición
  • Menor error humano: El compilador/runtime maneja la sincronización

Esquema de un Monitor:

┌──────────────────────────────────────────────┐
│              MONITOR                          │
│  Datos compartidos (privados)               │
├──────────────────────────────────────────────┤
│  ┌────────────────────────────────────────┐ │
│  │  Cola de entrada                       │ │
│  │  Threads esperan para entrar           │ │
│  └────────────────────────────────────────┘ │
├──────────────────────────────────────────────┤
│  procedimiento_sincronizado1() {            │
│    // Solo un thread ejecuta a la vez       │
│  }                                          │
│  procedimiento_sincronizado2() {            │
│    // Exclusión mutua garantizada           │
│  }                                          │
├──────────────────────────────────────────────┤
│  Variables de condición:                    │
│    - no_lleno.wait() / signal()             │
│    - no_vacio.wait() / signal()             │
└──────────────────────────────────────────────┘

Operaciones sobre variables de condición:

Operación Descripción
wait() Suspende el thread hasta que se haga signal()
signal() Despierta un thread en espera (si hay)
broadcast() Despierta TODOS los threads en espera

Deadlock (Bloqueo Mutuo)

Deadlock: Situación donde dos o más threads se esperan mutuamente de forma indefinida

Ejemplo clásico de Deadlock:

┌─────────────────────────────────────────────────┐
│  Thread A                                    │
├─────────────────────────────────────────────────┤
│  1. Adquiere Recurso 1 (Lock1)                │
│  2. Intenta adquirir Recurso 2 (Lock2)        │
│     ¡Lock2 está con Thread B! ESPERA...        │
│  3. (esperando indefinidamente)               │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│  Thread B                                    │
├─────────────────────────────────────────────────┤
│  1. Adquiere Recurso 2 (Lock2)                │
│  2. Intenta adquirir Recurso 1 (Lock1)        │
│     ¡Lock1 está con Thread A! ESPERA...        │
│  3. (esperando indefinidamente)               │
└─────────────────────────────────────────────────┘

RESULTADO: ¡Nadie avanza! Deadlock circular.

Ejemplo real:

Escenario del puente:

  • Coche A entra al puente de norte a sur
  • Coche B entra al puente de sur a norte
  • Ambos se encuentran en el medio
  • Ninguno puede avanzar sin que el otro retroceda
  • Si nadie retrocede → Deadlock

Condiciones Necesarias para Deadlock

Coffman: 4 condiciones que DEBEN ocurrir simultáneamente para deadlock
Condición Descripción Ejemplo
Exclusión Mutua Recurso solo puede usar un thread a la vez Una impresora, un lock
Retener y Esperar Thread mantiene recursos mientras espera otros Tiene Lock1, espera Lock2
Sin Apropiación Los recursos no pueden ser quitados por la fuerza No se puede quitar Lock1 a Thread A
Espera Circular Cadena circular de threads esperándose mutuamente A espera B, B espera A
Para prevenir deadlock, basta romper UNA de estas condiciones

Estrategias de prevención:

  • Romper exclusión mutua: Usar recursos compartidos cuando sea posible
  • Romper retener y esperar: Adquirir todos los recursos de una vez
  • Permitir apropiación: El SO puede quitar recursos (difícil de implementar)
  • Romper espera circular: Jerarquía de recursos (adquirir en orden)

Prevención y Evitación de Deadlock

Prevención de Deadlock

Romper una de las 4 condiciones:

Estrategia: Adquisición Ordenada

Regla: Siempre adquirir locks en el mismo orden

// Todos los threads adquieren:
Lock1 → Lock2 → Lock3

// Si Thread A tiene Lock1 y quiere Lock2
// Y Thread B tiene Lock2 y quiere Lock3
// NO hay deadlock porque B no quiere Lock1

Ventaja: Simple de implementar

Desventaja: Requiere disciplina

Estrategia: Adquisición Atómica

Regla: Adquirir todos los recursos juntos

// Adquirir Lock1 Y Lock2 juntos
lock(Lock1, Lock2) {
  // O adquiere ambos, o ninguno
}

// Si falla, liberar y reintentar

Ventaja: Garantiza sin deadlock

Desventaja: Menor paralelismo

Detección y Recuperación

  • Detección: El SO detecta ciclos en el grafo de recursos
  • Recuperación: Terminar uno de los threads involucrados
  • Costo: Sobrecarga del sistema

Ejercicios Conceptuales

Ejercicio 1: Productor-Consumidor

Problema: Un productor coloca items en un buffer finito. Un consumidor los retira. Si el buffer está lleno, el productor espera. Si está vacío, el consumidor espera.

Preguntas:

  1. ¿Qué mecanismo de sincronización usarías?
  2. ¿Cuántas variables de condición necesitas?
  3. ¿Qué pasa si hay múltiples productores y consumidores?

Discusión:

  • Mecanismo: Semáforos o Monitores
  • Variables: 2 (buffer_no_lleno, buffer_no_vacio)
  • Múltiples: Mismo mecanismo funciona con N threads

Ejercicio 2: Filósofos Comensales

Problema: 5 filósofos alrededor de una mesa. Cada uno tiene un palillo a izquierda y derecha. Para comer, necesita AMBOS palillos.

Preguntas:

  1. ¿En qué situación ocurre deadlock?
  2. ¿Cómo se puede prevenir?
  3. ¿Todos los filósofos comen eventualmente?

Discusión:

  • Deadlock: Todos toman el palillo izquierdo simultáneamente
  • Prevención: Un filósofo toma primero palillos ordenados
  • Inanición: Posible si algunos filósofos comen siempre

Ejercicio 3: Lectores-Escritores

Problema: Una base de datos permite múltiples lecturas simultáneas, pero solo una escritura a la vez. Lectores y escritores no pueden acceder simultáneamente.

Preguntas:

  1. ¿Cómo priorizas lectores vs escritores?
  2. ¿Puede ocurrir inanición de escritores?
  3. ¿Puede ocurrir inanición de lectores?

Discusión:

  • Prioridad lectores: Escritores pueden sufrir inanición
  • Prioridad escritores: Lectores esperan más
  • Balance: Mecanismos de equidad (FIFO)

Ejercicio 4: Problema de la Barbería

Problema: Una barbería con 1 barbero, N sillas de espera. Si no hay clientes, el barbero duerme. Si llega un cliente y el barbero duerme, lo despierta. Si la sala está llena, el cliente se va.

Preguntas:

  1. ¿Cuántos semáforos necesitas?
  2. ¿Qué variables de condición requieres?
  3. ¿Cómo manejas cuando la sala está llena?

Discusión:

  • Semáforo para sillas (contador)
  • Variable condición: clientes_esperando, barbero_listo
  • Sala llena: El cliente se va sin esperar

Ejercicio 5: Cena de los Sabios

Problema: Variante de filósofos donde solo 4 personas pueden comer simultáneamente (en lugar de 5).

Preguntas:

  1. ¿Por qué esto previene deadlock?
  2. ¿Qué condición de Coffman se rompe?
  3. ¿Es una solución justa?

Discusión:

  • Previene porque al menos 1 persona puede comer siempre
  • Rompe: Espera circular (no todos pueden estar esperando)
  • Injusto: Uno siempre come menos (posible inanición)
