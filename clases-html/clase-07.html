Objetivos de Aprendizaje

Resultado de Aprendizaje (RA3): Administra la memoria, los procesos de entrada y salida, la comunicación entre procesos y la sincronización de los mismos (Alineado con Evaluación E3).

Al finalizar esta clase, serás capaz de:

  1. Diferenciar entre procesos y threads (hilos)
  2. Entender los mecanismos de sincronización
  3. Explicar el problema de deadlock
  4. Resolver problemas clásicos de sincronización
  5. Analizar situaciones de bloqueo mutuo

Abreviaciones de Concurrencia

  • IPC (Inter-Process Communication): Comunicación entre procesos independientes.
  • Race Condition: Condición de carrera, fallo que ocurre cuando dos hilos acceden a un recurso al mismo tiempo.
  • FIFO (First-In, First-Out): El primero en entrar es el primero en salir.
  • LIFO (Last-In, First-Out): El último en entrar es el primero en salir (pilas).

Proceso vs Thread (Hilo)

Un hilo (thread) es la unidad básica de ejecución dentro de un proceso

Comparación Proceso vs Thread

Característica Proceso Thread
Espacio de direcciones Independiente y aislado Compartido entre threads
Recursos Propios (archivos, memoria) Compartidos del proceso
Comunicación IPC complejo (pipes, shared memory) Directa (memoria compartida)
Contexto Pesado ( PCB completo) Ligero (registros, stack)
Cambio de contexto Lento (miles de ciclos) Rápido (cientos de ciclos)
Creación Lenta y costosa Rápida y económica

┌─────────────────────────────────────────────────────┐
│                   PROCESO (ej. Chrome)               │

└─────────────────────────────────────────────────────┘

Ventajas de usar threads:

  • Responsividad: UI permanece activa mientras se procesa en background
  • Economía: Menos recursos que crear procesos
  • Compartición: Fácil acceso a recursos compartidos
  • Paralelismo: Aprovechar múltiples CPUs

Sincronización de Threads

💡 Analogías para entender la Sincronización

Si los conceptos técnicos te parecen difíciles, piensa en estas situaciones cotidianas:

  • Mutex (Exclusión Mutua): Es como la llave de un baño único en un café. Solo una persona puede tener la llave a la vez. Si quieres entrar y la llave no está, debes esperar a que la persona anterior la devuelva.
  • Semáforo: Es como un restaurante con 5 mesas. El "contador" empieza en 5. Cada vez que llega un grupo, el contador baja. Si llega a 0, los nuevos clientes deben esperar en la puerta hasta que alguien salga y el contador vuelva a subir.
  • Condición de Carrera: Es como si dos personas intentan escribir en la misma hoja de papel al mismo tiempo. Al final, el mensaje será un garabato ilegible porque ninguno respetó el turno del otro.
El problema técnico: Cuando múltiples threads acceden a datos compartidos simultáneamente

Condición de Carrera (Race Condition)

Tiempo    Thread A              Memoria          Thread B
────────────────────────────────────────────────────────────────
  t1      lee saldo (1000)      [saldo=1000]
  t2                            [saldo=1000]     lee saldo (1000)
  t3      suma 100 (local=1100)
  t4                                             resta 50 (local=950)
  t5      escribe 1100          [saldo=1100]
  t6                            [saldo=950]      escribe 950
────────────────────────────────────────────────────────────────
                                 RESULTADO: $950 (¡incorrecto!)
Una condición de carrera ocurre cuando el resultado depende del orden de ejecución

Mutex (Mutual Exclusion)

Mutex es un lock que permite solo un thread a la vez en una sección crítica

Características del Mutex:

  • Propiedad: El thread que lo adquiere es el único que puede liberarlo
  • Exclusión: Solo un thread puede tener el mutex a la vez
  • Bloqueo: Si el mutex está ocupado, el thread espera
  • Sección crítica: Código que accede a recursos compartidos

Operaciones básicas:

┌─────────────────────────────────────────────────┐
│  Thread 1                │  Thread 2          │
├─────────────────────────────────────────────────┤
│  lock(mutex)             │                    │
│  // Sección crítica      │  lock(mutex)       │
│  modificar_compartido()  │  // Espera...      │
│  unlock(mutex)           │  // Espera...      │
│                          │  // Se libera...   │
│                          │  // Sección crítica│
│                          │  modificar_compartido()│
│                          │  unlock(mutex)     │
└─────────────────────────────────────────────────┘

Ejemplo conceptual (sin código):

Escenario: Dos cajeros acceden a la misma cuenta bancaria

  • Sin mutex: Ambos leen al mismo tiempo → resultado inconsistente
  • Con mutex: Uno accede primero, termina, luego el otro → resultado correcto

Semáforos

Un semáforo es un contador entero que controla el acceso a recursos

Tipos de Semáforos:

Semáforo Binario (0 o 1)

  • Similar a un mutex
  • Un solo recurso disponible
  • Usado para exclusión mutua
  • S = 1: recurso libre
  • S = 0: recurso ocupado
wait(S):  // Adquirir
  while S == 0;  // Espera si está ocupado
  S = 0;

signal(S):  // Liberar
  S = 1;

Semáforo Contador (0 a N)

  • N recursos idénticos
  • Hasta N threads pueden acceder
  • Usado para pool de recursos
  • S = N: N recursos libres
  • S = 0: todos ocupados
wait(S):  // Adquirir
  while S == 0;  // Espera si no hay recursos
  S = S - 1;

signal(S):  // Liberar
  S = S + 1;

Ejemplo de uso - Pool de conexiones:

Semáforo con valor inicial = 5 (5 conexiones disponibles)

  • Thread A hace wait(): semáforo = 4
  • Thread B hace wait(): semáforo = 3
  • Thread C hace wait(): semáforo = 2
  • Thread A termina y hace signal(): semáforo = 3
  • Thread D hace wait(): semáforo = 2

Monitores

Un monitor es una estructura de alto nivel que encapsula datos y métodos de sincronización

Características de los Monitores:

  • Encapsulamiento: Datos y métodos sincronizados en una unidad
  • Exclusión automática: Solo un thread puede estar activo en el monitor
  • Colas de espera: Threads esperan en variables de condición
  • Menor error humano: El compilador/runtime maneja la sincronización

Esquema de un Monitor:

┌──────────────────────────────────────────────┐
│              MONITOR                          │
│  Datos compartidos (privados)               │
├──────────────────────────────────────────────┤
│  ┌────────────────────────────────────────┐ │
│  │  Cola de entrada                       │ │
│  │  Threads esperan para entrar           │ │
│  └────────────────────────────────────────┘ │
├──────────────────────────────────────────────┤
│  procedimiento_sincronizado1() {            │
│    // Solo un thread ejecuta a la vez       │
│  }                                          │
│  procedimiento_sincronizado2() {            │
│    // Exclusión mutua garantizada           │
│  }                                          │
├──────────────────────────────────────────────┤
│  Variables de condición:                    │
│    - no_lleno.wait() / signal()             │
│    - no_vacio.wait() / signal()             │
└──────────────────────────────────────────────┘

Operaciones sobre variables de condición:

Operación Descripción
wait() Suspende el thread hasta que se haga signal()
signal() Despierta un thread en espera (si hay)
broadcast() Despierta TODOS los threads en espera

Deadlock (Bloqueo Mutuo)

Deadlock: Situación donde dos o más threads se esperan mutuamente de forma indefinida

Ejemplo clásico de Deadlock:

┌─────────────────────────────────────────────────┐
│  Thread A                                    │
├─────────────────────────────────────────────────┤
│  1. Adquiere Recurso 1 (Lock1)                │
│  2. Intenta adquirir Recurso 2 (Lock2)        │
│     ¡Lock2 está con Thread B! ESPERA...        │
│  3. (esperando indefinidamente)               │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│  Thread B                                    │
├─────────────────────────────────────────────────┤
│  1. Adquiere Recurso 2 (Lock2)                │
│  2. Intenta adquirir Recurso 1 (Lock1)        │
│     ¡Lock1 está con Thread A! ESPERA...        │
│  3. (esperando indefinidamente)               │
└─────────────────────────────────────────────────┘

RESULTADO: ¡Nadie avanza! Deadlock circular.

Ejemplo real:

Escenario del puente:

  • Coche A entra al puente de norte a sur
  • Coche B entra al puente de sur a norte
  • Ambos se encuentran en el medio
  • Ninguno puede avanzar sin que el otro retroceda
  • Si nadie retrocede → Deadlock

Condiciones Necesarias para Deadlock

Coffman: 4 condiciones que DEBEN ocurrir simultáneamente para deadlock
Condición Descripción Ejemplo
Exclusión Mutua Recurso solo puede usar un thread a la vez Una impresora, un lock
Retener y Esperar Thread mantiene recursos mientras espera otros Tiene Lock1, espera Lock2
Sin Apropiación Los recursos no pueden ser quitados por la fuerza No se puede quitar Lock1 a Thread A
Espera Circular Cadena circular de threads esperándose mutuamente A espera B, B espera A
Para prevenir deadlock, basta romper UNA de estas condiciones

Estrategias de prevención:

  • Romper exclusión mutua: Usar recursos compartidos cuando sea posible
  • Romper retener y esperar: Adquirir todos los recursos de una vez
  • Permitir apropiación: El SO puede quitar recursos (difícil de implementar)
  • Romper espera circular: Jerarquía de recursos (adquirir en orden)

Prevención y Evitación de Deadlock

Prevención de Deadlock

Romper una de las 4 condiciones:

Estrategia: Adquisición Ordenada

Regla: Siempre adquirir locks en el mismo orden

// Todos los threads adquieren:
Lock1 → Lock2 → Lock3

// Si Thread A tiene Lock1 y quiere Lock2
// Y Thread B tiene Lock2 y quiere Lock3
// NO hay deadlock porque B no quiere Lock1

Ventaja: Simple de implementar

Desventaja: Requiere disciplina

Estrategia: Adquisición Atómica

Regla: Adquirir todos los recursos juntos

// Adquirir Lock1 Y Lock2 juntos
lock(Lock1, Lock2) {
  // O adquiere ambos, o ninguno
}

// Si falla, liberar y reintentar

Ventaja: Garantiza sin deadlock

Desventaja: Menor paralelismo

Detección y Recuperación

  • Detección: El SO detecta ciclos en el grafo de recursos
  • Recuperación: Terminar uno de los threads involucrados
  • Costo: Sobrecarga del sistema

🔧 Ejercicios Prácticos (Parte 1)

Ejercicio Práctico 1: Observación de Threads en Linux

Tiempo: 15 minutos | Recurso: Webminal o JSLinux

Objetivo: Observar threads reales de procesos en ejecución

  1. Abre una terminal Linux
  2. Ejecuta: ps -eLf | head -20 (muestra procesos y threads)
  3. Identifica la columna LWP (Light Weight Process = Thread ID)
  4. Busca un proceso con múltiples threads: ps -eLf | grep firefox (si está instalado) o ps -eLf | grep bash
  5. Cuenta: ¿Cuántos threads tiene el proceso systemd (PID 1)?
  6. Compara: ps aux | wc -l vs ps -eLf | wc -l. ¿Por qué la diferencia?
Explicación: El comando ps -eLf muestra cada thread en una línea separada, mientras que ps aux agrupa por proceso. La diferencia en el conteo te dice cuántos threads hay en el sistema.

Ejercicio Práctico 2: Análisis de /proc para Threads

Tiempo: 15 minutos | Recurso: Webminal o JSLinux

Objetivo: Explorar la información de threads en el sistema de archivos /proc

  1. Encuentra tu shell actual: echo $$ (muestra el PID)
  2. Lista los threads de tu shell: ls /proc/$$/task/
  3. Observa: Cada número en ese directorio es un Thread ID (TID)
  4. Entra a un thread: cd /proc/$$/task/[primer número]
  5. Mira su estado: cat status | grep State
  6. Documenta: ¿Cuántos threads tiene tu shell? ¿En qué estado están?
Descubrimiento: Incluso procesos simples como bash pueden tener múltiples threads para manejar señales, jobs en background, etc.

Ejercicio Práctico 3: Simulación de Condición de Carrera

Tiempo: 20 minutos | Recurso: Webminal

Objetivo: Entender cómo ocurre una race condition

  1. Crea un archivo compartido: echo 100 > /tmp/saldo.txt
  2. Abre dos terminales (o dos sesiones en Webminal)
  3. En Terminal 1, ejecuta repetidamente: saldo=$(cat /tmp/saldo.txt); echo $((saldo + 10)) > /tmp/saldo.txt
  4. En Terminal 2, ejecuta repetidamente: saldo=$(cat /tmp/saldo.txt); echo $((saldo - 5)) > /tmp/saldo.txt
  5. Después de 10 segundos en ambas, verifica: cat /tmp/saldo.txt
  6. Pregunta: ¿El resultado es 150 (100 + 10*10 - 5*10)? ¿Por qué sí o por qué no?
Análisis: Si el resultado no es 150, es porque ocurrió una race condition. Ambos procesos leyeron el mismo valor, modificaron, y el último en escribir "ganó", perdiendo la actualización del otro.

Ejercicio Práctico 4: Identificación de Bloqueos (Híbrido)

Parte A (Linux): Busque procesos en estado D (uninterruptible sleep): ps aux | grep ' D '. Esto indica que el proceso está esperando un recurso (normalmente E/S) que no puede ser interrumpido.

Parte B (Windows): Abra el Monitor de Recursos (resmon) → Pestaña CPU. Si ve un proceso en color rojo, haga clic derecho → Analizar cadena de espera. Windows le mostrará exactamente qué proceso está bloqueando a otro.

Ejercicio Práctico 5: Análisis de Archivos Bloqueados

Tiempo: 15 minutos | Recurso: Webminal

Objetivo: Entender cómo los archivos pueden causar bloqueos

  1. Crea un archivo de bloqueo: touch /tmp/mi_bloqueo.lock
  2. Abre el archivo en modo exclusivo (terminal 1): exec 200>/tmp/mi_bloqueo.lock; flock -x 200
  3. Intenta abrirlo en otra terminal: flock -x /tmp/mi_bloqueo.lock -c "echo Hola"
  4. Observa: El segundo comando espera hasta que el primero libere el lock
  5. Libera el lock (terminal 1): Presiona Ctrl+C o cierra la terminal
  6. Documenta: ¿Qué mecanismo de sincronización estás observando?
Conexión: Esto es similar a un mutex a nivel de sistema de archivos. El comando flock implementa un lock exclusivo (como un mutex binario).

📝 Ejercicios Conceptuales (Parte 2)

Ejercicio Conceptual 1: Productor-Consumidor

Problema: Un productor coloca items en un buffer finito. Un consumidor los retira. Si el buffer está lleno, el productor espera. Si está vacío, el consumidor espera.

Preguntas:

  1. ¿Qué mecanismo de sincronización usarías?
  2. ¿Cuántas variables de condición necesitas?
  3. ¿Qué pasa si hay múltiples productores y consumidores?

Discusión:

  • Mecanismo: Semáforos o Monitores
  • Variables: 2 (buffer_no_lleno, buffer_no_vacio)
  • Múltiples: Mismo mecanismo funciona con N threads

Ejercicio Conceptual 2: Filósofos Comensales

Problema: 5 filósofos alrededor de una mesa. Cada uno tiene un palillo a izquierda y derecha. Para comer, necesita AMBOS palillos.

Preguntas:

  1. ¿En qué situación ocurre deadlock?
  2. ¿Cómo se puede prevenir?
  3. ¿Todos los filósofos comen eventualmente?

Discusión:

  • Deadlock: Todos toman el palillo izquierdo simultáneamente
  • Prevención: Un filósofo toma primero palillos ordenados
  • Inanición: Posible si algunos filósofos comen siempre

Ejercicio Conceptual 3: Análisis de Deadlock en Sistemas Reales

Escenario: En tu ejercicio práctico 4, encontraste procesos bloqueados.

Preguntas:

  1. ¿Cuáles de las 4 condiciones de Coffman se cumplían en cada caso?
  2. ¿Era un deadlock real o solo un proceso esperando I/O?
  3. Si hubiera sido deadlock, ¿qué estrategia usarías para recuperarte?

Ejercicio de Refuerzo: Explorando Hilos y Sincronización

Objetivo: Familiarizarte con conceptos de hilos y sincronización mediante ejemplos prácticos.

Actividades sugeridas:

  1. Observa los hilos de un proceso:
    • Abre una terminal y ejecuta: ps -eLf | grep bash
    • ¿Cuántas columnas "LWP" (hilos) ves?
    • Esto muestra que hasta un simple shell usa múltiples hilos
  2. Entiende la condición de carrera:
    • Imagina que tú y un compañero intentan editar el mismo archivo de Word al mismo tiempo
    • ¿Qué problemas podrían ocurrir?
    • ¿Cómo los prevenirías? (pista: un solo usuario a la vez)
  3. Piensa en deadlock:
    • Dos personas entran a una habitación con dos puertas
    • Persona A bloquea puerta 1 y espera puerta 2
    • Persona B bloquea puerta 2 y espera puerta 1
    • ¿Pueden salir? ¿Cómo evitarías esto?
Consejo: Estos conceptos pueden parecer abstractos al principio. La clave es relacionarlos con situaciones de la vida real. No te preocupes si no los dominas de inmediato.
