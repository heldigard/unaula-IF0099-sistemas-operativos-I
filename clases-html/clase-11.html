1. El Hardware de Almacenamiento

El SO debe gestionar la diferencia abismal de velocidad entre la CPU (nanosegundos) y el Almacenamiento (milisegundos).

HDD (Disco Mecánico)

  • Búsqueda física: Latencia alta (~10ms) por movimiento de cabezales.
  • Platos y Sectores: El dato se lee mediante magnetismo en discos que giran.
  • Falla: Si el cabezal toca el plato (head crash), los datos se pierden.

SSD / NVMe (Estado Sólido)

  • Sin partes móviles: Latencia ultra-baja (~0.1ms).
  • Chips de memoria: Almacena electrones en celdas NAND.
  • Velocidad: Hasta 7000 MB/s en PCIe 4.0.

2. Particionado: El Mapa del Disco

Antes de que el SO pueda ver carpetas, debe definir cómo se divide el espacio físico en el disco.

EsquemaLímites ProfesionalesUso Actual
MBR (Legacy)Máximo 2TB y 4 particiones primarias.Sistemas industriales o antiguos.
GPT (Moderno)Hasta 9.4 ZB y 128 particiones.Estándar para servidores Cloud y UEFI.

Firma de Arranque

El sector de arranque (Sector 0) contiene el código que carga el SO. Si ese sector se daña, el hardware dirá "No bootable device found" aunque sus archivos estén intactos.

3. Métodos de Entrada/Salida (I/O)

¿Cómo se comunica la CPU con los discos?

  • E/S Programada: La CPU lee byte por byte. Desperdicia ciclos de reloj esperando al disco lento.
  • E/S por Interrupciones: El disco avisa a la CPU: "¡Ya terminé de leer!". La CPU solo trabaja cuando el dato está listo.
  • DMA (Direct Memory Access): El disco copia datos directamente a la RAM sin pasar por la CPU. Fundamental en servidores web para no saturar el procesador.

4. Comandos de Auditoría de Discos

Auditoría en Linux (Bash)

# Ver salud física (S.M.A.R.T)
sudo smartctl -a /dev/sda

# Benchmark de lectura real
sudo hdparm -tT /dev/sda

# Ver latencia de E/S en vivo
iostat -xz 1

# Ver procesos escribiendo a disco
sudo iotop -o

Auditoría en Windows (PowerShell)

# Ver salud física del disco
Get-PhysicalDisk | Get-StorageReliabilityCounter

# Optimizar (Defrag/TRIM)
Optimize-Volume -DriveLetter C -ReTrim

# Analizar colas de disco
Get-Counter "\PhysicalDisk(*)\Avg. Disk Queue Length"

# Ver particiones detalladas
Get-Partition -DriveLetter C

5. Actividad Práctica Híbrida: Salud de Almacenamiento

Laboratorio: Diagnóstico de Latencia UCS

Objetivo: Identificar si el disco está frenando el rendimiento del proyecto.

Tarea 1: Benchmarking real (Linux)

  1. Instale sysstat: sudo apt install sysstat.
  2. Ejecute iostat -xz 1 10 mientras copia un archivo grande.
  3. Observe la columna await. Si es > 20ms, su disco es el cuello de botella.

Tarea 2: Análisis de Colas (Windows)

  1. Abra PerfMon → Agregue el contador PhysicalDisk \ Avg. Disk Queue Length.
  2. Realice una búsqueda masiva de archivos (Ctrl+F). Observe cómo sube la cola. Si pasa de 2 por disco, el sistema se "congelará" para el usuario.

Tarea 3: Espacios de Almacenamiento

En Windows, use diskmgmt.msc para identificar si sus discos son Dinámicos o Básicos. Investigue qué ventaja tiene un disco Dinámico para un servidor de archivos.

Entregable: Una tabla con la velocidad de lectura de su disco Linux vs su disco Windows y su análisis de cuál sistema parece gestionar mejor la cola de peticiones.

Casos Reales: E/S en Producción

Caso 1: HDD en Servidor de Base de Datos

Escenario: Un servidor con PostgreSQL tiene discos HDD tradicionales. Las consultas son lentas.

Diagnóstico:

  1. iostat -x 1 muestra %util > 80% constantemente
  2. La cola de disco (avgqu-sz) > 2
  3. La latencia (await) > 50ms

Solución: Migrar a SSD NVMe paraDB. EI/OPS de SSD es 100x mayor.

Caso 2: Disco "Sin Espacio" Pero No Está Lleno

Escenario: El disco muestra 90% usado pero aún hay espacio.

Causa: Inodos agotados (Linux) - demasiados archivos pequeños.

Solución:

# Ver inodos disponibles
df -i

# Encontrar carpetas con muchos archivos
find / -xdev -type f | cut -d/ -f3 | sort | uniq -c | sort -nr | head

Caso 3: Servidor con Ruido (Clicking)

Escenario: El disco hace ruidos extraños. Posible falla de hardware.

Solución:

# Verificar salud SMART
sudo smartctl -H /dev/sda

# Ver errores recientes
sudo smartctl -l error /dev/sda

📈 Análisis de Patrones de I/O

Aleatorio vs Secuencial:

  • I/O Secuencial: HDD eficiente (cabeza lee continuamente). Ideal para: videos, backups.
  • I/O Aleatorio: SSD/NVMe superior (sin cabezal mecánico). Ideal para: BD, sistemas de archivos.
# Monitorear patrones de I/O en tiempo real
iostat -x 1

# Columnas importantes:
# await: Latencia promedio (ms) - >20ms indica problema
# %util: Porcentaje de uso - >80% saturado
# r/s, w/s: Operaciones de lectura/escritura por segundo

🔥 Caso Real: "El Cuello de Botella de la Base de Datos"

Escenario: Un servidor PostgreSQL con discos HDD tiene consultas lentas.

# Diagnóstico paso a paso:

# 1. Verificar utilización del disco
iostat -xz 1
# Si %util > 80% constantemente → disco saturado

# 2. Ver colas de disco
# avgqu-sz > 2 indica acumulación de peticiones

# 3. Ver latencia
# await > 20ms indica cuello de botella

# 4. Identificar procesos
iotop -o

Solución: Migrar datos a SSD/NVMe. Considerar RAID 10 para BD críticas.

🔧 Troubleshooting Guide: Discos Lentos

# 1. Diagnóstico rápido con iostat
iostat -xz 1 10 | tee disk_stats.txt

# 2. Ver procesos que generan I/O
sudo iotop -aoP --batch -n 5

# 3. Ver uso de disco por proceso
sudo dstat -d --top-io-adv 5

# 4. Verificar estado SMART
sudo smartctl -a /dev/sda | grep -E "(Reallocated|Current_Pending|Offline_Uncorrectable)"

# 5. Análisis de colas histórico
sar -d 1 10
