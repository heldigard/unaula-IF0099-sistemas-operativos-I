1. El Modelo UGO (User, Group, Others)

Linux utiliza un sistema de permisos de 9 bits para controlar el acceso. Cada archivo pertenece a un **Usuario** y a un **Grupo**.

# [Tipo][u][g][o]
- rwx r-x r--  1 helder developers 1024 Apr 15 06:00 config.php
# 7   5   4 (Octal)

Principio del Menor Privilegio

NUNCA use 777. Un servidor profesional debe tener los permisos mínimos necesarios para funcionar. Si una carpeta es para el servidor web, el dueño debe ser www-data y los permisos 750.

2. Bits Especiales: SUID, SGID y Sticky Bit

PermisoOctalEfecto Laboral
SUID4000El proceso corre con los privilegios del DUEÑO del archivo (ej: passwd).
SGID2000Los archivos creados en esta carpeta heredan el grupo del padre (Colaboración).
Sticky1000Solo el dueño del archivo puede borrarlo (ej: carpeta /tmp).

3. ACLs (Access Control Lists)

¿Qué pasa si necesitas que el Usuario A lea, el B escriba y el C no haga nada? El modelo UGO es insuficiente. Las ACLs permiten permisos por usuario específico.

# Ver ACLs actuales
getfacl archivo.txt

# Dar permiso de lectura solo a 'maria'
setfacl -m u:maria:r-- archivo.txt

4. Hardening: Reduciendo la Superficie de Ataque

Hardening es cerrar todas las "puertas" innecesarias del servidor.

  • SSH: Cambiar puerto 22 y prohibir login de root.
  • Firewall: Bloquear todo lo entrante excepto HTTP/S y SSH.
  • Servicios: Apagar lo que no se usa (ej: Avahi, Bluetooth en servers).

5. Seguridad Avanzada: SELinux y AppArmor

Además de los permisos tradicionales (UGO), Linux ofrece sistemas de seguridad Mandatory Access Control (MAC) que limitan lo que cada proceso PUEDE hacer, no solo lo que tiene permiso de hacer.

SELinux (Security-Enhanced Linux)

Desarrollado por la NSA. Es el más robusto y complejo. Usa políticas que definen qué procesos pueden acceder a qué archivos.

# Ver estado de SELinux
getenforce

# Cambiar modo (Enforcing/Permissive)
sudo setenforce 1

# Ver contexto de seguridad de un archivo
ls -Z /var/www/html

# Ver contexto de un proceso
ps -Z | grep apache

Casos de uso: Servidores gubernamentales, bancarios, infraestructura crítica.

AppArmor

Más simple que SELinux. Usa perfiles basados en rutas (path-based). Ubuntu lo usa por defecto.

# Ver estado de AppArmor
sudo apparmor_status

# Ver perfiles cargados
ls /etc/apparmor.d/

# Perfil para Apache
cat /etc/apparmor.d/usr.sbin.apache2

# Modo aprendizaje (generar perfil)
sudo aa-complain /usr/sbin/apache2

Casos de uso: Servidores web, aplicaciones desktop, Ubuntu Server.

¿Cuál elegir?

  • SELinux: Máxima seguridad, pero curva de aprendizaje alta. Ideal para RHEL/CentOS/Fedora.
  • AppArmor: Más fácil de configurar, suficiente para la mayoría. Ideal para Ubuntu/Debian.

6. Modelos de Control de Acceso

Entender estos modelos es fundamental para diseñar políticas de seguridad efectivas.

Modelo Descripción Ejemplo Uso Profesional
DAC
(Discretionary)		 El propietario del archivo decide quién puede acceder. Permisos Linux (chmod), NTFS Servidores generales
MAC
(Mandatory)		 El SO define políticas obligatorias. El usuario no puede cambiarlas. SELinux, AppArmor Servidores sensibles
RBAC
(Role-Based)		 Los permisos se asignan a roles, no a usuarios directamente. Active Directory, sudo Empresas medianas/grandes

Enfoque Profesional: Defense in Depth

Los servidores seguros usan múltiples capas:

  1. Capa 1: Permisos DAC (dueño, grupo, otros)
  2. Capa 2: RBAC (grupos de AD, sudo)
  3. Capa 3: MAC (SELinux/AppArmor)

Casos Reales: Seguridad Linux en Producción

Caso 1: Servidor Hackeado vía SSH

Escenario: Encuentras un archivo sospechoso llamado .hidden/backdoor.sh. El servidor está enviando tráfico extraño a Internet.

Diagnóstico:

# Ver últimas conexiones
last | head -20

# Ver procesos sospechosos
ps auxf

# Ver archivos modificados recientemente
find / -mtime -1 -type f 2>/dev/null | head -20

Caso 2: Permisos 777 en Producción

Escenario: Un desarrollador puso chmod 777 a todo el proyecto por "facilidad".

Problema: Cualquier usuario puede leer y modificar archivos sensibles.

Solución:

# Encontrar archivos con permisos incorrectos
find /var/www -type f -perm 777

# Corregir permisos estándar
chmod 755 /var/www
chmod -R 644 /var/www/*.html
chmod -R 755 /var/www/cgi-bin

✅ Checklist de Hardening: CIS Benchmarks Simplificada

1. Configuración de SSH

# Editar /etc/ssh/sshd_config
PermitRootLogin no
PasswordAuthentication no  # Usar solo claves
MaxAuthTries 3
ClientAliveInterval 300
ClientAliveCountMax 0
AllowUsers usuario1 usuario2
Port 2222  # Cambiar del puerto por defecto

2. Firewall (UFW)

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 2222/tcp       # Puerto SSH cambiado
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw limit 2222/tcp       # Protección brute-force
sudo ufw enable

3. Actualizaciones Automáticas

sudo apt install unattended-upgrades
sudo dpkg-reconfigure unattended-upgrades

# Configurar /etc/apt/apt.conf.d/50unattended-upgrades
Unattended-Upgrade::Remove-Unused-Dependencies "true";
Unattended-Upgrade::Remove-Unused-Kernel-Packages "true";

4. Desactivar Servicios Innecesarios

# Listar servicios
systemctl list-unit-files --type=service --state=enabled

# Desactivar servicios comúnmente innecesarios en servers
sudo systemctl disable bluetooth
sudo systemctl disable cups      # Impresión
sudo systemctl disable avahi-daemon  # Zeroconf
sudo systemctl disable bluetooth

# Ver puertos abiertos
sudo ss -tulpn

5. Fail2Ban (Protección Brute-Force)

sudo apt install fail2ban
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local

# Configurar /etc/fail2ban/jail.local
[sshd]
enabled = true
port = 2222
filter = sshd
logpath = /var/log/auth.log
maxretry = 3
bantime = 3600

sudo systemctl restart fail2ban
sudo fail2ban-client status sshd

🚨 Casos de Incidentes: Brechas de Seguridad Famosas

Caso 1: Equifax (2017) - 147 millones de registros

  • Causa: Apache Struts sin parchear (CVE-2017-5638)
  • Prevenible con: Actualizaciones automáticas + WAF
  • Lección: unattended-upgrades o sistema de patching

Caso 2: MongoDB sin Autenticación (2016-2019)

  • Causa: Bases de datos MongoDB expuestas a internet sin password
  • Prevenible con: UFW + autenticación + bind a localhost
  • Comandos: sudo ufw deny 27017 + enable auth en mongod.conf

Caso 3: Proxmox CVE-2021-4034 (PwnKit)

  • Causa: Escalada de privilegios en polkit
  • Prevenible con: SELinux/AppArmor + actualizaciones
  • Verificación: getenforce debe retornar "Enforcing"

🔥 UFW Avanzado: Configuraciones Específicas

# === CONFIGURACIONES AVANZADAS UFW ===

# 1. Rate limiting específico
sudo ufw limit log 22/tcp    # Logear intentos SSH
sudo ufw limit 2222/tcp      # Limitar conexiones SSH alternativo

# 2. Permitir desde IP específica
sudo ufw allow from 192.168.1.100 to any port 22
sudo ufw allow from 10.0.0.0/8 to any port 3306  # Solo LAN para MySQL

# 3. Denegar IP específica
sudo ufw deny from 192.168.1.200

# 4. Permitir rango de puertos
sudo ufw allow 60000:61000/udp  # Para Mosh

# 5. Bloquear red completa pero permitir una IP
sudo ufw deny from 192.168.1.0/24
sudo ufw allow from 192.168.1.50

# 6. Reglas por aplicación
sudo ufw app list              # Ver aplicaciones disponibles
sudo ufw allow 'Nginx Full'    # Abre 80 y 443

# 7. Ver reglas numeradas
sudo ufw status numbered

# 8. Eliminar regla por número
sudo ufw delete 2

🛡️ SELinux/AppArmor Básico

SELinux (RHEL/CentOS/Fedora)

# Ver estado actual
getenforce                    # Enforcing / Permissive / Disabled
sestatus                      # Información detallada

# Cambiar modo temporalmente (hasta reinicio)
sudo setenforce 0             # Modo permisivo (log pero no bloquea)
sudo setenforce 1             # Modo enforcing (protección activa)

# Ver contexto de archivos
ls -Z /var/www/html

# Cambiar contexto de archivo
sudo chcon -t httpd_sys_content_t /var/www/html/archivo.html

# Restaurar contexto por defecto
sudo restorecon -Rv /var/www/html

AppArmor (Ubuntu/Debian)

# Ver estado
sudo apparmor_status

# Ver perfiles cargados
ls /etc/apparmor.d/

# Cambiar modo de perfil
sudo aa-complain /usr/sbin/nginx   # Modo permissive (solo log)
sudo aa-enforce /usr/sbin/nginx    # Modo enforcing (protección activa)

# Generar perfil nuevo
sudo aa-genprof /usr/bin/miaplicacion

# Recargar todos los perfiles
sudo service apparmor reload

🔐 ACLs Complejos: Escenarios Avanzados

# === ESCENARIO 1: Directorio de proyecto con múltiples roles ===

# Crear estructura
sudo mkdir -p /srv/proyecto/{docs,codigo,logs}

# Establecer dueño y grupo base
sudo chown -R root:developers /srv/proyecto
sudo chmod 750 /srv/proyecto

# ACLs específicas:

# 1. Desarrolladores: Acceso total a docs y codigo
sudo setfacl -R -m g:developers:rwx /srv/proyecto/docs
sudo setfacl -R -m g:developers:rwx /srv/proyecto/codigo
sudo setfacl -R -m g:developers:r-x /srv/proyecto/logs

# 2. Auditores: Solo lectura de docs
sudo setfacl -R -m g:auditores:r-x /srv/proyecto/docs

# 3. Jefe de proyecto: Acceso total a todo
sudo setfacl -R -m u:jefe:rwx /srv/proyecto

# 4. Usuario externo: Solo lectura de docs específicos
sudo setfacl -m u:consultor:r-- /srv/proyecto/docs/resumen.txt

# 5. Default ACLs (herencia para nuevos archivos)
sudo setfacl -d -R -m g:developers:rwx /srv/proyecto/codigo
sudo setfacl -d -R -m o::--- /srv/proyecto/codigo

# Verificar configuración
getfacl /srv/proyecto/codigo

# === ESCENARIO 2: Eliminar ACLs ===

# Eliminar ACL específica
sudo setfacl -x u:consultor /srv/proyecto/docs/resumen.txt

# Eliminar todas las ACLs y volver a permisos básicos
sudo setfacl -b /srv/proyecto
