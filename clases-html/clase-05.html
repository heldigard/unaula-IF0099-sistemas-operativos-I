1. Inspección Forense de Procesos

En Linux, el directorio /proc es una "ventana" al kernel. Cada número de carpeta es un PID activo. Un administrador usa comandos para traducir esos archivos en información útil.

Snapshot: El comando ps

Muestra el estado estático. Vital para auditorías y logs.

# Los 5 procesos que más RAM consumen
ps aux --sort=-%mem | head -n 6

# Ver hilos (threads) de un proceso
ps -eLf | grep apache2

# Jerarquía completa (Árbol)
pstree -p

Interactivo: top y htop

htop es el estándar visual. Permite matar procesos, ver uso por cada núcleo de CPU y filtrar por nombre.

Comando Pro: Presione Shift + P en top para ver quién está "incendiando" la CPU.

2. Control de Procesos: El Sistema de Señales

Un proceso no se "apaga"; el kernel le envía una **Señal**. Es un mensaje asíncrono que el proceso debe manejar.

SeñalNúmeroEfecto Laboral
SIGTERM15Cierre amable. El proceso guarda datos y libera memoria. Es el default de kill.
SIGKILL9Cierre forzado. El kernel borra el proceso de RAM sin aviso. ¡Usar solo en bloqueos!
SIGHUP1Reload. Servidores y aplicaciones recargan su configuración sin detenerse.
SIGSTOP19Congelar. Detiene la ejecución sin borrarlo de la memoria.

3. Gestión de Prioridades: Nice y Renice

El planificador de Linux usa el valor nice (-20 a 19) para decidir quién es el "mejor ciudadano" del servidor.

  • -20: Prioridad Máxima (VIP). Reservado para procesos críticos.
  • 19: Prioridad Mínima. El proceso solo corre si nadie más necesita la CPU.
# Lanzar un backup pesado con prioridad mínima
nice -n 19 tar -czf backup.tar.gz /home/usuario/documentos

# Bajar la prioridad de un proceso que ya está corriendo
sudo renice -n 10 -p [PID]

4. Administración de Servicios: systemd

En el mundo empresarial, los procesos de servidor (Web, BD, SSH) corren como Daemons gestionados por el sistema de inicialización.

Comandos Vitales de systemctl

sudo systemctl status apache2   # ¿Está funcionando o falló?
sudo systemctl restart nginx    # Aplicar cambios de configuración
sudo systemctl enable docker    # Iniciar automáticamente al encender
journalctl -u ssh -f           # Ver errores del servicio en tiempo real

Casos Reales de Administración de Procesos

Estos escenarios están basados en incidentes reales en centros de datos.

Caso 1: Memory Leak en Producción

Escenario: Un servidor Java con Tomcat muestra que después de 48 horas de operación, la memoria RAM usada pasa del 30% al 95%. Los servicios comienzan a fallar por falta de memoria.

Tu rol como SRE/DevOps:

  1. ¿Qué herramienta usarías para identificar qué proceso consume más memoria?
  2. Si identificas que es un proceso específico, ¿cómo obtienes un "heap dump" para análisis?
  3. ¿Cuál sería tu solución inmediata (sin reiniciar todo) vs solución definitiva?

Comandos clave: ps aux --sort=-%mem, top, jmap -heap [PID]

Caso 2: Servicio que No Responde a SIGTERM

Escenario: Intentas detener Nginx con systemctl stop nginx pero después de 90 segundos el proceso sigue activo. El servicio queda en estado "failed" pero los procesos hijos siguen corriendo.

Tu rol como administrador:

  1. ¿Qué significa que un servicio no responde a SIGTERM (señal 15)?
  2. ¿Qué diferencias hay entre SIGTERM, SIGKILL y SIGHUP?
  3. ¿Cómo forzarías el cierre limpio de una aplicación que no responde?

Comandos clave: kill -15 [PID], kill -9 [PID], pkill -9 nginx

Caso 3: Priorización de Procesos en Peak

Escenario: Es lunes a las 8AM y tu servidor de base de datos tiene 500 conexiones de usuarios. Un job de analytics programado para las 8AM comienza a correr y slows down todas las consultas de usuarios.

Tu rol como administrador:

  1. ¿Cómo identificas qué proceso/job está causando la desaceleración?
  2. ¿Qué valor de "nice" le darías al proceso de analytics?
  3. ¿Cómo ejecutas un proceso con baja prioridad desde el inicio?

Comandos clave: nice -n 19 [comando], ionice -c 3 [comando]

🚨 Troubleshooting Guide: "Mi proceso se colgó"

¿El proceso no responde?

├─▶ ¿Está corriendo? → ps aux | grep nombre

│ ├─▶ Sí → ¿Está en estado D (Uninterruptible Sleep)?

│ │ ├─▶ Sí → Proceso bloqueado en I/O → Revisar disco/red

│ │ └─▶ No → Continuar

│ └─▶ No → El proceso terminó o nunca inició

│

├─▶ ¿Cuánto CPU usa? → top -p PID

│ ├─▶ 0% CPU → Puede estar esperando I/O o deadlocked

│ ├─▶ 100% CPU → Loop infinito o procesamiento intensivo

│ └─▶ Normal → Revisar logs

│

├─▶ ¿Qué archivos tiene abiertos? → lsof -p PID

│ └─▶ ¿Alguno bloqueado o en NFS caído?

│

├─▶ ¿En qué está trabajando? → strace -p PID

│ └─▶ ¿Repetiendo la misma syscall?

│

├─▶ ¿Logs de error? → journalctl -u servicio -n 50

│ └─▶ ¿Out of memory? ¿Segmentation fault?

│

└─▶ Intentar recuperación:

├─▶ kill -15 PID (SIGTERM - cierre amable)

├─▶ Esperar 10-30 segundos

├─▶ ¿Sigues vivo? → kill -9 PID (SIGKILL - forzar)

└─▶ ¿No muere? → Proceso zombie/defunct → Requiere reinicio

🔍 Ejercicios de Filtrado Avanzado con ps, grep, awk

Ejercicio 1: Procesos por usuario y ordenados por memoria

# Encuentra los 5 procesos que más RAM consumen de un usuario específico
ps aux --sort=-%mem | grep "^usuario" | head -n 5

# Versión más elegante con awk
ps aux | awk '$1 == "usuario" {print $0}' | sort -k4 -nr | head -n 5

Ejercicio 2: Encontrar procesos huérfanos

# Procesos cuyo padre (PPID) es 1 (init/systemd)
ps aux | awk '$3 == 1 {print $2, $11}' | head -10

# Contar cuántos procesos huérfanos hay
echo "Procesos huérfanos: $(ps aux | awk '$3 == 1' | wc -l)"

Ejercicio 3: Procesos que más tiempo de CPU han acumulado

# Ordenar por tiempo total de CPU (columna 10)
ps aux --sort=-time | head -n 10

# Mostrar solo PID, usuario, %CPU, tiempo y comando
ps aux --sort=-time | awk '{printf "%-8s %-10s %6s %10s %s\n", $2, $1, $3, $10, $11}' | head -n 10

Ejercicio 4: Script de auditoría completo

#!/bin/bash
# audit_procesos.sh - Reporte de procesos críticos

echo "=== REPORTE DE PROCESOS - $(date) ==="
echo ""
echo "🔴 Top 5 por CPU:"
ps aux --sort=-%cpu | head -n 6 | tail -n 5 | awk '{printf "%-10s %6s %s\n", $1, $3, $11}'

echo ""
echo "🔴 Top 5 por Memoria:"
ps aux --sort=-%mem | head -n 6 | tail -n 5 | awk '{printf "%-10s %6s %s\n", $1, $4, $11}'

echo ""
echo "🔴 Procesos Zombies:"
ps aux | awk '$8 ~ /^Z/ {print $0}'
if [ $? -ne 0 ]; then
    echo "No hay procesos zombie ✓"
fi

echo ""
echo "🔴 Procesos con más de 100 hilos:"
ps aux | awk '$6 > 100 {print $2, $6, $11}'

📖 Caso de Incidente Real: El Proceso Zombie que Colapsó el Servidor

🕐 Hora 0 - Todo normal

Un servidor de aplicaciones Java con Tomcat procesa 500 requests/segundo normalmente.

🕒 Hora 4 - Alerta de monitoreo

El sistema de monitoreo (Nagios) alerta: "Cannot fork: Resource temporarily unavailable"

# Ver procesos del sistema
ps aux | wc -l
# Resultado: 32768 procesos (!!!)

🕓 Hora 4:15 - Diagnóstico

# Buscar zombies
ps aux | grep "^Z"
# Cientos de procesos en estado Z

# ¿Quién es el padre?
ps aux | grep "^Z" | awk '{print $3}' | sort | uniq -c | sort -nr | head
# El padre es el proceso Java principal

🔍 Causa Raíz:

  • La aplicación Java lanzaba procesos externos para generar reportes PDF
  • El código Java NO llamaba wait() para recolectar los procesos hijos
  • Cada reporte generado dejaba un proceso zombie
  • Después de 4 horas, la tabla de procesos se llenó (max 32768)
  • El kernel no pudo crear más procesos → "Cannot fork"

💊 Solución:

  1. Reinicio de emergencia del servicio Tomcat (mató al padre, recolectó zombies)
  2. Fix del código Java: agregar process.waitFor() después de cada exec()
  3. Monitoreo preventivo: alerta si el conteo de procesos supera 5000

📊 Métricas después del fix:

  • Tiempo de vida de proceso hijo: < 5 segundos (antes: infinito)
  • Procesos totales en el sistema: ~200 (antes: 32768)
  • Uptime del servidor: 99.99% (después del fix)

🎯 Mejores Prácticas SRE para Monitoreo de Procesos

Métrica Comando/Tool Umbral de Alerta Acción
Load Average uptime > número de cores Investigar procesos que consumen CPU
Context Switches vmstat 1 > 50,000/seg Posible thrashing, revisar número de procesos
Procesos Zombie ps aux | grep ^Z > 10 Identificar y reiniciar proceso padre
File Descriptors lsof -p PID | wc -l > 80% del límite Aumentar límite o fix memory leak
Hilos por Proceso ps -eLf | grep PID | wc -l > 500 Revisar thread pool configuration
Swap Usage free -h > 20% Aumentar RAM o investigar memory leak
Tiempo de CPU Acumulado ps aux --sort=-time Anomalías Identificar procesos runaway

🛠️ Script de monitoreo SRE básico:

#!/bin/bash
# sre_health_check.sh

ALERT_FILE="/var/log/sre_alerts.log"

# Check 1: Load Average
LOAD=$(uptime | awk -F'load average:' '{print $2}' | awk '{print $1}' | tr -d ',')
CORES=$(nproc)
if (( $(echo "$LOAD > $CORES" | bc -l) )); then
    echo "$(date): ALERTA - Load average $LOAD supera cores ($CORES)" >> $ALERT_FILE
fi

# Check 2: Procesos Zombie
ZOMBIES=$(ps aux | grep -c "^Z")
if [ $ZOMBIES -gt 10 ]; then
    echo "$(date): ALERTA - $ZOMBIES procesos zombie detectados" >> $ALERT_FILE
fi

# Check 3: Context Switches (usar vmstat en bucle)
CS=$(vmstat 1 2 | tail -1 | awk '{print $12}')
if [ $CS -gt 50000 ]; then
    echo "$(date): ALERTA - Context switches alto: $CS/seg" >> $ALERT_FILE
fi

echo "$(date): Health check completado" >> /var/log/sre_health.log
