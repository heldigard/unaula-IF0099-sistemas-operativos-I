1. El Modelo UGO (User, Group, Others)

Linux utiliza un sistema de permisos de 9 bits para controlar el acceso. Cada archivo pertenece a un **Usuario** y a un **Grupo**.

# [Tipo][u][g][o]
- rwx r-x r--  1 helder developers 1024 Apr 15 06:00 config.php
# 7   5   4 (Octal)

Principio del Menor Privilegio

NUNCA use 777. Un servidor profesional debe tener los permisos mínimos necesarios para funcionar. Si una carpeta es para el servidor web, el dueño debe ser www-data y los permisos 750.

2. Bits Especiales: SUID, SGID y Sticky Bit

PermisoOctalEfecto Laboral
SUID4000El proceso corre con los privilegios del DUEÑO del archivo (ej: passwd).
SGID2000Los archivos creados en esta carpeta heredan el grupo del padre (Colaboración).
Sticky1000Solo el dueño del archivo puede borrarlo (ej: carpeta /tmp).

3. ACLs (Access Control Lists)

¿Qué pasa si necesitas que el Usuario A lea, el B escriba y el C no haga nada? El modelo UGO es insuficiente. Las ACLs permiten permisos por usuario específico.

# Ver ACLs actuales
getfacl archivo.txt

# Dar permiso de lectura solo a 'maria'
setfacl -m u:maria:r-- archivo.txt

4. Hardening: Reduciendo la Superficie de Ataque

Hardening es cerrar todas las "puertas" innecesarias del servidor.

  • SSH: Cambiar puerto 22 y prohibir login de root.
  • Firewall: Bloquear todo lo entrante excepto HTTP/S y SSH.
  • Servicios: Apagar lo que no se usa (ej: Avahi, Bluetooth en servers).

5. Seguridad Avanzada: SELinux y AppArmor

Además de los permisos tradicionales (UGO), Linux ofrece sistemas de seguridad Mandatory Access Control (MAC) que limitan lo que cada proceso PUEDE hacer, no solo lo que tiene permiso de hacer.

SELinux (Security-Enhanced Linux)

Desarrollado por la NSA. Es el más robusto y complejo. Usa políticas que definen qué procesos pueden acceder a qué archivos.

# Ver estado de SELinux
getenforce

# Cambiar modo (Enforcing/Permissive)
sudo setenforce 1

# Ver contexto de seguridad de un archivo
ls -Z /var/www/html

# Ver contexto de un proceso
ps -Z | grep apache

Casos de uso: Servidores gubernamentales, bancarios, infraestructura crítica.

AppArmor

Más simple que SELinux. Usa perfiles basados en rutas (path-based). Ubuntu lo usa por defecto.

# Ver estado de AppArmor
sudo apparmor_status

# Ver perfiles cargados
ls /etc/apparmor.d/

# Perfil para Apache
cat /etc/apparmor.d/usr.sbin.apache2

# Modo aprendizaje (generar perfil)
sudo aa-complain /usr/sbin/apache2

Casos de uso: Servidores web, aplicaciones desktop, Ubuntu Server.

¿Cuál elegir?

  • SELinux: Máxima seguridad, pero curva de aprendizaje alta. Ideal para RHEL/CentOS/Fedora.
  • AppArmor: Más fácil de configurar, suficiente para la mayoría. Ideal para Ubuntu/Debian.

6. Modelos de Control de Acceso

Entender estos modelos es fundamental para diseñar políticas de seguridad efectivas.

Modelo Descripción Ejemplo Uso Profesional
DAC
(Discretionary)		 El propietario del archivo decide quién puede acceder. Permisos Linux (chmod), NTFS Servidores generales
MAC
(Mandatory)		 El SO define políticas obligatorias. El usuario no puede cambiarlas. SELinux, AppArmor Servidores sensibles
RBAC
(Role-Based)		 Los permisos se asignan a roles, no a usuarios directamente. Active Directory, sudo Empresas medianas/grandes

Enfoque Profesional: Defense in Depth

Los servidores seguros usan múltiples capas:

  1. Capa 1: Permisos DAC (dueño, grupo, otros)
  2. Capa 2: RBAC (grupos de AD, sudo)
  3. Capa 3: MAC (SELinux/AppArmor)

7. Comandos de Auditoría de Seguridad

Auditoría de Acceso

# Ver intentos fallidos de login
sudo lastb | head -n 10

# Ver bloqueos por fuerza bruta
sudo faillock --user estudiante

# Ver puertos abiertos y quién los usa
sudo ss -tulpn

Auditoría de Sistema

# Buscar archivos con SUID (Peligrosos)
find / -perm -4000 -type f 2>/dev/null

# Ver reglas del Firewall activo
sudo ufw status numbered

# Ver historial de comandos con tiempo
export HISTTIMEFORMAT="%F %T " && history

8. Actividad Práctica: Blindaje del Nodo Linux (Insumo E4)

Laboratorio: Asegurando UCS Linux

Objetivo: Implementar seguridad multicapa en el nodo Linux.

Tarea 1: ACLs Corporativas

  1. Cree el directorio /srv/ucs_web.
  2. Use setfacl para que solo el grupo www-data y su usuario personal tengan acceso total. Otros usuarios no deben ni poder entrar (permiso 0).

Tarea 2: Hardening del Firewall

  1. Active el firewall: sudo ufw enable.
  2. Permita el tráfico para el servidor web: sudo ufw allow 80/tcp y sudo ufw allow 443/tcp.
  3. Limite el SSH para evitar ataques de fuerza bruta: sudo ufw limit ssh.

Tarea 3: Auditoría

  1. Use ss -tlnp para verificar que solo los puertos autorizados están escuchando conexiones externas.

Entregable: Una captura del comando getfacl sobre su carpeta de servicios y de ufw status para la Evaluación E4.

Casos Reales: Seguridad Linux en Producción

Caso 1: Servidor Hackeado vía SSH

Escenario: Encuentras un archivo sospechoso llamado .hidden/backdoor.sh. El servidor está enviando tráfico extraño a Internet.

Diagnóstico:

# Ver últimas conexiones
last | head -20

# Ver procesos sospechosos
ps auxf

# Ver archivos modificados recientemente
find / -mtime -1 -type f 2>/dev/null | head -20

Caso 2: Permisos 777 en Producción

Escenario: Un desarrollador puso chmod 777 a todo el proyecto por "facilidad".

Problema: Cualquier usuario puede leer y modificar archivos sensibles.

Solución:

# Encontrar archivos con permisos incorrectos
find /var/www -type f -perm 777

# Corregir permisos estándar
chmod 755 /var/www
chmod -R 644 /var/www/*.html
chmod -R 755 /var/www/cgi-bin
