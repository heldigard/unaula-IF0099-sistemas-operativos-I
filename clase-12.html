1. Introducción a la Protección y Seguridad

Pregunta fundamental: ¿Cómo evitamos que un proceso malicioso borre archivos importantes? ¿Cómo prevenimos que un usuario acceda a información confidencial?

¿Qué es Protección?

Protección se refiere a los mecanismos internos del SO para controlar el acceso a los recursos del sistema. Es una cuestión de política de control de acceso:

  • ¿Quién puede acceder a qué recurso?
  • ¿Qué operaciones puede realizar (lectura, escritura, ejecución)?
  • ¿Cómo se garantiza esto?

¿Qué es Seguridad?

Seguridad se refiere a las defensas contra amenazas externas:

  • Malware: Virus, gusanos, ransomware
  • Ataques de red: Intrusos, sniffing, DoS
  • Ataques locales: Elevación de privilegios, exploits
  • Ingeniería social: Phishing, suplantación
Distinción clave: Protección es sobre control interno; seguridad es sobre defensa externa.

2. Protección vs Seguridad

Aspecto Protección Seguridad
Objetivo Controlar acceso entre procesos legítimos Defender contra amenazas externas
Enfoque Prevenir abusos internos Prevenir ataques externos
Ejemplo Que un usuario no borre archivos de otro Que un virus no infecte el sistema
Mecanismos Permisos, dominios, ACL Firewalls, antivirus, cifrado

🛡️ Protección

  • Control de accesos
  • Autenticación de usuarios
  • Permisos de archivos
  • Aislamiento de procesos

🔒 Seguridad

  • Firewall
  • Antivirus
  • Cifrado de datos
  • Detección de intrusiones

3. Principios de Protección

Principio de Mínimo Privilegio

Regla de oro: Un proceso debe tener exactamente los privilegios que necesita para realizar su tarea, ni más ni menos.

Este principio minimiza el daño potencial si un proceso es comprometido.

Ejemplos:

# ❌ MAL: Servidor web corriendo como root
sudo httpd    # Tiene acceso total al sistema

# ✅ BIEN: Servidor web con usuario dedicado
chown -R www-data:www-data /var/www
su - www-data
httpd       # Solo puede acceder a /var/www
# ❌ MAL: Cliente de correo con permisos de administrador
sudo thunderbird   # Puede leer cualquier archivo

# ✅ BIEN: Cliente de correo como usuario normal
thunderbird         # Solo sus propios archivos

Principio de Falla Segura

Si un mecanismo de protección falla, debe negar el acceso por defecto en lugar de permitirla.

Ejemplo: Si un firewall falla, debe bloquear todo el tráfico en lugar de permitir todo.

4. Dominios de Protección

Un dominio de protección es un conjunto de permisos que se aplican a un proceso o usuario.

Jerarquía de Dominios

┌─────────────────────────────────────────────────────┐
│  Sistema (Ring 0) - Kernel                              │
│  - Acceso total al hardware                                    │
│  - Puede acceder a toda la memoria                             │
├─────────────────────────────────────────────────────┤
│  Supervisor (Ring 1) - SO                                   │
│  - Gestiona procesos, memoria, E/S                            │
│  - Puede crear dominios de usuario                                │
├─────────────────────────────────────────────────────┤
│  Usuario (Ring 3) - Aplicaciones                          │
│  - Acceso limitado a sus propios recursos                     │
│  - No puede acceder directamente al hardware                      │
└─────────────────────────────────────────────────────┘

Ejemplo de Dominios en Unix

# Usuario root (dominio privilegiado)
root@server:~# cat /etc/shadow    # ✅ Puede leer
root@server:~# fdisk /dev/sda      # ✅ Puede particionar
root@server:~# kill -9 1234        # ✅ Puede matar procesos

# Usuario ordinario (dominio sin privilegios)
usuario@server:~$ cat /etc/shadow   # ❌ Permiso denegado
usuario@server:~$ fdisk /dev/sda     # ❌ Operación no permitida
usuario@server:~$ kill -9 1234       # ❌ Solo procesos propios

5. Matriz de Acceso

La matriz de acceso es un modelo conceptual que muestra qué procesos tienen acceso a qué objetos.

Objetos
Dominios Archivo A Archivo B Dispositivo
Proceso 1 ✅ Leer - -
Proceso 2 ✅ Leer, Escribir - -
Proceso 3 - ✅ Leer ✅ Abrir
Proceso 4 - - ✅ Leer, Escribir
Nota: Esta matriz es conceptual. En la práctica, se implementa mediante ACLs (Listas de Control de Acceso) o capabilities.

6. Permisos en Unix/Linux

Modelo UGO (User, Group, Others)

Unix usa un modelo de permisos basado en tres categorías:

Categoría Símbolo Descripción
User (u) Primer triplet (rwx) Dueño del archivo
Group (g) Segundo triplet (rwx) Grupo del archivo
Others (o) Tercer triplet (rwx) Resto de usuarios

Tipos de Permisos

r - Read    (leer)
w - Write   (escribir)
x - eXecute (ejecutar)

Notación Octal

-rwxr-xr-x  1 juan developers 1024 Feb 15 10:30 archivo.txt
│  │  │     │     │     │       │
│  │  │     │     │     │       │
│  │  │     │     │     │       │
└──┴──┴─────┴─────┴─────┴─────┴─────┴───
   │  │     │     │     │       │
   │  │     │     │     │       │
   └──┴─────┴─────┴─────┴─────┘
      │     │
      └─┴───┘
      6   4   4
    rwx r-x r-x
Cálculo rápido:
r = 4, w = 2, x = 1 → 4+2+1 = 7 → rwx
Para directorios: rwx = 4+2+1 = 7, directorio necesita x para entrar

7. Permisos Especiales en Linux

SUID (Set User ID)

Cuando se ejecuta un archivo con SUID, el proceso corre con los privilegios del dueño del archivo, no del usuario que lo ejecuta.

# Ejemplo: /usr/bin/passwd
$ ls -l /usr/bin/passwd
-rwsr-xr-x  1 root root 73465 Feb 15 10:30 /usr/bin/passwd
 │             │     │
 │             │     └─→ Dueño = root
 │             └─→ s = SUID activo

$ cat /etc/shadow    # Solo root puede leer
$ passwd              # Sin embargo, cualquier usuario puede cambiar su clave

# ¿Cómo funciona? passwd se ejecuta como root temporalmente

SGID (Set Group ID)

Similar a SUID, pero para grupos. Útil para directorios compartidos.

# Crear directorio colaborativo
mkdir /proyecto
chown -R :developers /proyecto
chmod g+s /proyecto        # SGID activo

# Cualquier archivo creado en /proyecto pertenece al grupo developers
ls -ld /proyecto
drwxrwsr-x  2 root developers 4096 Feb 15 10:30 /proyecto
 │                │
                └─→ s = SGID activo

Sticky Bit

Usado típicamente en directorios compartidos como /tmp. Solo el propietario de un archivo puede borrarlo, incluso si otros tienen permisos de escritura.

# Ejemplo: /tmp
$ ls -ld /tmp
drwxrwxrwt  10 root root 4096 Feb 15 10:30 /tmp
 │                │
                └─→ t = Sticky bit activo

$ touch /tmp/archivo1.txt
$ chmod 777 /tmp/archivo1.txt

# Otro usuario puede escribir en el archivo
$ echo "hola" >> /tmp/archivo1.txt   # ✅ Puede escribir

# Pero NO puede borrarlo (si no es el propietario)
$ rm /tmp/archivo1.txt               # ❌ Permission denied

8. Amenazas Comunes y Defensas

Buffer Overflow

El ataque clásico más común. Ocurre cuando un programa escribe más allá del límite de un buffer en memoria.

// Código vulnerable
void vulnerable(char* input) {
    char buf[64];           // Buffer de 64 bytes
    strcpy(buf, input);     // ❌ No verifica longitud!
}

// Ataque
vulnerable("AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAABBBBBB");
// Escribe más de 64 bytes, sobrescribe la pila de retorno

Defensas contra Buffer Overflow

Mecanismo Qué hace
ASLR Randomiza las direcciones de memoria
NX bit Marca ciertas áreas de memoria como no ejecutable
Stack Canaries Inserta valores de verificación entre variables
Fortify Source Extensiones de GCC que verifican llamadas a funciones

Ingeniería Social

Ataques que engañan a usuarios para que revelen información sensible.

Ejemplo de Phishing: 
"Estimado usuario: su cuenta será bloqueada en 24 horas. Haga clic aquí para verificar: http://banco-seguro.com (sitio falso)"

Defensas

  • Educación: Enseñar a identificar URLs sospechosas
  • Verificación: Siempre verificar la URL real antes de hacer clic
  • Autenticación de dos factores (2FA)
  • Filtros de correo: Detectar phishing

9. Mecanismos de Defensa

Mecanismo Tipo Qué protege
Autenticación Preventiva Acceso no autorizado
Cifrado Preventiva/Detectiva Intercepción de datos
Firewall Preventiva Tráfico malicioso de red
Antivirus Detectiva Malware, virus
IDS/IPS Detectiva/Preventiva Intrusos, ataques

10. Actividad Práctica

Ejercicio 1: Ver Permisos

# Ver permisos detallados
ls -l /etc/passwd /etc/shadow

# Ver tu usuario y grupos
id

# Crear archivo de prueba
touch prueba_permisos.txt
ls -l prueba_permisos.txt

# Cambiar permisos
chmod 750 prueba_permisos.txt    # rwxr-xr---
ls -l prueba_permisos.txt

# Ver propietario y grupo
stat prueba_permisos.txt

Ejercicio 2: SUID en Acción

# Buscar archivos con SUID
find / -perm -4000 -user root 2>/dev/null | head -10

# Ver archivos SGID
find / -perm -2000 -group 2>/dev/null | head -10

# Analizar un SUID conocido
ls -l /usr/bin/sudo
ls -l /usr/bin/passwd
ls -l /usr/bin/su
Nota: Los archivos SUID/SGID son potenciales vectores de escalada de privilegios si tienen vulnerabilidades.

Ejercicio 3: Sticky Bit

# Crear directorio compartido
mkdir /tmp/compartido

# Activar sticky bit
chmod +t /tmp/compartido

# Crear archivos como diferentes usuarios
# (simulado - en práctica real necesitarías múltiples usuarios)
echo "Desde usuario 1" > /tmp/compartido/arch1.txt
echo "Desde usuario 2" > /tmp/compartido/arch2.txt

# Intentar borrar archivo de otro usuario
rm /tmp/compartido/arch1.txt    # Error si no eres propietario

Tiempo estimado: 30 minutos
