1. SRE: Site Reliability Engineering

La ingeniería de confiabilidad es la disciplina que aplica principios de ingeniería de software a problemas de operaciones de sistemas.

Métricas Clave (SLAs / SLIs)

  • Disponibilidad (Uptime): Porcentaje del tiempo que el servicio web está arriba.
  • Latencia: Tiempo de respuesta promedio de Apache/IIS.
  • Tasa de Errores: Porcentaje de peticiones que fallan (Error 500).

2. Pruebas de Estrés: Llevando el SO al Límite

¿Qué pasa con la RAM si llegan 1000 usuarios a la vez? ¿Cómo reacciona el kernel?

Herramientas Linux

  • stress-ng: Carga artificial de CPU y RAM.
  • Apache Benchmark (ab): Genera miles de peticiones HTTP.

Herramientas Windows

  • CPUSTRES: (Sysinternals) Controla la carga por hilo individual.
  • Performance Monitor: Graba el impacto en disco durante el pico.

3. QA del Sistema Operativo

Antes de la sustentación, debe validar la integridad de su infraestructura:

  1. Prueba de Reinicio (Cold Boot): ¿Suben los servicios automáticamente? ¿El RAID se monta solo?
  2. Prueba de Conectividad: ¿El Nodo Windows puede ver el portal de Linux? ¿Las IPs son estáticas?
  3. Prueba de Seguridad: ¿El puerto 22 está realmente bloqueado desde afuera?

5. Actividad Práctica: Simulacro de Desastres

Taller de Pre-Sustentación

Objetivo: Preparar el sistema para las preguntas de parrilla del docente.

Tarea 1: Stress Test (Linux)

  1. Instale stress-ng: sudo apt install stress-ng.
  2. Lanza carga de memoria: stress-ng --vm 2 --vm-bytes 1G --timeout 60s.
  3. Observe en htop cómo el SO gestiona la presión de RAM. ¿Se activó el Swap?

Tarea 2: HTTP Benchmark

  1. Desde Linux, ataque su servidor Windows: ab -n 1000 -c 10 http://[IP_WINDOWS]:8080/.
  2. Vea cuántas peticiones por segundo soporta su IIS virtualizado.

Tarea 3: QA Final Checklist

  • Verifique que /etc/fstab tiene el UUID correcto.
  • Verifique que las llaves SSH funcionan sin contraseña (Hardening).
  • Limpie archivos temporales y logs de prueba para entregar un sistema "limpio".

Entregable: Un video corto (máx 3 min) donde demuestre que tras reiniciar ambas VMs, los servidores web Apache e IIS están en línea sin intervención manual.

Casos Reales: SRE y QA en Producción

Caso 1: El Servidor que Caía a las 2 AM

Escenario: Un servidor de base de datos MySQL caía cada noche a las 2:00 AM exactamente. Los logs no mostraban errores. Era un job de backup que consumía toda la RAM.

Cómo se resolvió:

# Linux: Monitoreo con htop top
htop

# Ver consumo de memoria por proceso
ps aux --sort=-%mem | head -10

# Ver logs de cron
sudo tail -f /var/log/cron

# Crear alerta
grep "OOM" /var/log/syslog

Lección: Siempre programa trabajos pesados (backups) en horas de baja actividad y configura monitoreo de memoria.

Caso 2: IIS Muere tras Actualización de Windows

Escenario: Después de instalar actualizaciones de Windows Server, IIS no iniciaba. Error 503 en el sitio web.

Diagnóstico:

# Ver estado de IIS
Get-Service W3SVC

# Ver logs de error
Get-Content C:\Windows\System32\LogFiles\HTTPERR\*.log -Tail 50

# Ver eventos
Get-EventLog -LogName System -Source IIS* -Newest 20

Solución:

# Reiniciar IIS
iisreset

# Si persiste, verificar Application Pools
Get-WebAppPoolState

# Reconstruir configuración si es necesario
aspnet_regiis -ua
aspnet_regiis -i

Caso 3: La Prueba de Carga que Derribó el Prod

Escenario: Un tester corrió Apache Benchmark contra el servidor de producción (no de prueba) pensando que era QA. El servidor se sobrecargó.

Prevención:

  • Entornos separados: NUNCA ejecutes pruebas de estrés en producción.
  • Rate limiting: Configura límites en Apache para prevenir DDoS accidentales.
  • Alertas: Configura alertas cuando CPU > 90% o memoria > 85%.

Ejercicio: Monitoreo y Alertas

Configura un sistema de monitoreo básico:

  3. ambos: Configura una tarea programada (cron/scheduler) que ejecute el monitoreo cada 5 minutos.
