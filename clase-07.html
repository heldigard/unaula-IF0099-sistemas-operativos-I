1. Hilos (Threads): La Multitarea Interna

Un hilo es la unidad de ejecución más pequeña del procesador. Mientras un proceso es el contenedor de recursos (Memoria, Archivos), el hilo es el ejecutor real de las instrucciones.

Lo que comparten

  • Código del programa
  • Variables globales (Data)
  • Heap (Memoria dinámica)
  • Sockets de red y archivos

Lo que es privado

  • Stack (Pila): Variables locales
  • Registros de CPU
  • Program Counter (PC)
  • Identificador (TID)

Hilos de Kernel vs Usuario

Kernel Threads: Gestionados por el SO. Permiten paralelismo real en CPUs multinúcleo.

User Threads: Gestionados por librerías. Rápidos pero si uno se bloquea en I/O, el proceso entero se detiene.

2. Sincronización: Evitando el Caos

Cuando dos hilos intentan modificar el mismo dato compartido al mismo tiempo, ocurre una Race Condition (Condición de Carrera). El resultado final es aleatorio.

3. Herramientas de Exclusión Mutua

Para proteger la Sección Crítica (el código que toca datos compartidos), usamos cerraduras lógicas.

HerramientaTipoUso Profesional
MutexCerradura (0/1)Proteger un objeto único (ej: una variable de contador).
SemáforoContador (0-N)Limitar acceso a un pool (ej: solo 5 hilos pueden imprimir).
MonitorObjeto SincronizadoUso en lenguajes como Java (synchronized) o C#.

💡 Analogía del Baño

Un Mutex es la llave de un baño único. Quien la tiene entra. Los demás esperan en la cola (estado Waiting) hasta que la llave sea devuelta a la recepción (unlock).

4. Deadlock: El Abrazo de la Muerte

Es el estado donde un grupo de hilos están bloqueados esperando recursos que otros hilos del mismo grupo poseen. Nadie avanza nunca.

🎭 Analogía del Puente Estrecho

Dos coches llegan a un puente de un solo carril desde direcciones opuestas. El coche A tiene la llave de la entrada norte, el coche B tiene la llave de la entrada sur. Ambos esperan que el otro retroceda, pero ninguno lo hace. Eso es un deadlock.

4.1 Las 4 Condiciones de Coffman (Todas deben cumplirse)

1️⃣ Exclusión Mutua

¿Qué significa? Los recursos no son compartibles. Solo un hilo puede usar el recurso a la vez.

Ejemplo: Una impresora solo puede imprimir un documento a la vez.

2️⃣ Retener y Esperar

¿Qué significa? Un hilo que tiene recursos puede pedir más recursos sin soltar los que ya tiene.

Ejemplo: El hilo A tiene el archivo X y pide el archivo Y. No suelta X mientras espera.

3️⃣ Sin Apropiación

¿Qué significa? Un recurso no puede ser quitado por la fuerza. Solo se libera voluntariamente por el hilo que lo posee.

Ejemplo: El SO no puede "robarle" la impresora a un hilo. Debe esperar a que termine.

4️⃣ Espera Circular

¿Qué significa? Existe una cadena circular de hilos donde cada uno espera un recurso que posee el siguiente.

Ejemplo: A espera recurso de B → B espera recurso de C → C espera recurso de A

✅ Solución: Romper al menos UNA condición

  • Exclusión mutua: Hacer recursos compartibles (ej: spooling de impresión)
  • Retener y esperar: Pedir todos los recursos al inicio o soltar antes de pedir nuevos
  • Sin apropiación: Permitir que el SO "robe" recursos (difícil de implementar)
  • Espera circular: ORDENAR LOS RECURSOS - pedir siempre en el mismo orden (ej: siempre primero A, luego B)

💡 La más usada en la práctica: Ordenar los recursos jerárquicamente

4.2 Ejemplo Práctico de Deadlock en Código

// DOS HILOS - DOS MUTEX

pthread_mutex_t mutex_A; // Recurso A

pthread_mutex_t mutex_B; // Recurso B

 

// HILO 1

void* hilo_1(void* arg) {

  pthread_mutex_lock(&mutex_A); // ✅ Obtiene A

  sleep(1); // Simula trabajo

  pthread_mutex_lock(&mutex_B); // ⏳ Espera B...

  // NUNCA LLEGA AQUÍ

}

 

// HILO 2

void* hilo_2(void* arg) {

  pthread_mutex_lock(&mutex_B); // ✅ Obtiene B

  sleep(1); // Simula trabajo

  pthread_mutex_lock(&mutex_A); // ⏳ Espera A...

  // NUNCA LLEGA AQUÍ

}

 

// RESULTADO: DEADLOCK - Ambos hilos esperan forever

🔧 Cómo evitarlo en el ejemplo anterior

Solución: Ambos hilos deben pedir los mutex EN EL MISMO ORDEN:

  • Siempre primero A, luego B (nunca B primero)
  • O pedir ambos al inicio con pthread_mutex_lock de forma atómica

⚠️ Síntomas de Deadlock en Producción

  • La aplicación "se congela" pero no consume CPU
  • Los logs dejan de actualizarse en puntos específicos
  • Timeout en operaciones que deberían ser rápidas
  • En logs: hilos esperando mutex que nunca se liberan

Herramientas de diagnóstico: jstack (Java), pstack (Linux), kill -3 (genera thread dump)

5. Comandos de Diagnóstico Profesional

Análisis en Linux (Bash)

# Ver hilos de un proceso (LWP)
ps -eLf | grep apache2

# Monitor interactivo de hilos
top -H

# Ver archivos bloqueados por apps
sudo lsof +L1

# Buscar hilos en estado D (bloqueo I/O)
ps aux | awk '$8=="D"'

Análisis en Windows (PS)

# Contar hilos totales del sistema
(Get-Process).Threads.Count | Measure-Object -Sum

# Ver hilos y su estado
Get-Process chrome | 
Select-Object -ExpandProperty Threads

# Ver bloqueos de archivos (Handle)
.\handle.exe C:\Windows\System32

6. Actividad Práctica Híbrida: Diagnóstico de Bloqueos

Laboratorio de Hilos UCS

Objetivo: Identificar y resolver cuellos de botella por sincronización.

Tarea 1: Wait Chain Analysis (Windows)

  1. Abra el Administrador de Tareas → Detalles.
  2. Busque un proceso pesado (Navegador, IDE). Clic derecho → Analyze Wait Chain.
  3. Identifique si hay hilos bloqueados esperando a otros procesos.

Tarea 2: Hilos del Kernel (Linux)

  1. Ejecute top -H.
  2. Observe los hilos con nombre kworker. Estos son hilos del kernel que realizan el trabajo sucio del SO (E/S, interrupciones).
  3. Identifique cuántos hilos tiene su shell: ls /proc/self/task | wc -l.

Tarea 3: Simulación de Contención (Linux)

  1. Terminal 1: Bloquee un archivo: flock /tmp/ucs.lock sleep 100.
  2. Terminal 2: Intente entrar: flock -n /tmp/ucs.lock echo "Entré" || echo "BLOQUEADO".
  3. Documente cómo el SO evita la colisión de datos.

Entregable: Una captura de pantalla de Analyze Wait Chain (Windows) o top -H (Linux) explicando qué información técnica le da esa herramienta para mejorar el rendimiento del servidor.

Casos Reales: Hilos y Concurrencia en Producción

Caso 1: Aplicación Bloqueada por Demasiados Hilos

Escenario: Tu aplicación web no responde. Los usuarios ven "Service Unavailable". Al revisar, hay cientos de hilos intentando escribir a la vez en una aplicación con múltiples hilos.

Diagnóstico y Solución:

  1. En Linux: ps -eLf | grep aplicacion | wc -l para contar hilos
  2. En Windows: (Get-Process -Name aplicacion).Threads.Count
  3. Implementa un pool de procesos con límite (ej: máximo 20 procesos simultáneos)
  4. Usa Mutex o Semáforo para proteger la sección crítica de escritura

Caso 2: Servidor que Queda Bloqueado (Deadlock)

Escenario: El servidor deja de responder completamente. No acepta nuevas conexiones. Un proceso está esperando un recurso que él mismo posee.

Diagnóstico:

  1. Linux: ps aux | awk '$8=="D"' para ver procesos en estado D (espera ininterrumpible)
  2. Windows: Usa procdump -ma [PID] para hacer dump de memoria y analizar
  3. Reinicia el servicio afectado; si persiste, reinicia el servidor completo

Caso 3: Race Condition en Archivo de Log

Escenario: Múltiples procesos escriben al mismo archivo de log. Algunas líneas se pierden o se entremezclan caracteres.

Solución:

# Linux: Usar flock para proteger la escritura
exec 200>/var/log/miapp.log
flock 200
echo "$(date): Mensaje de log" >&200
flock -u 200

Analogía: "El Restaurante Multihilo"

El escenario: Imagina un restaurante con múltiples meseros (hilos), cocineros (procesadores) y una cocina compartida (memoria).

┌─────────────────────────────────────────────────────────────┐ │ RESTAURANTE UCS │ ├─────────────────────────────────────────────────────────────┤ │ MESERO 1 MESERO 2 MESERO 3 ← Hilos (threads) │ │ ↓ ↓ ↓ │ │ ┌──────┐ ┌──────┐ ┌──────┐ │ │ │Pedido│ │Pedido│ │Pedido│ ← Cada uno lleva orden │ │ └──┬───┘ └──┬───┘ └──┬───┘ │ │ └───────────┼───────────┘ │ │ ↓ │ │ ╔═══════════════════════════════════════════════════════╗ │ │ ║ COCINA COMPARTIDA ║ │ │ ║ ┌──────────┐ ┌──────────┐ ┌──────────┐ ║ │ │ ║ │ Chef CPU │ │ Chef CPU │ │ HORNO │ ← Recursos ║ │ │ ║ └──────────┘ └──────────┘ └──────────┘ ║ │ │ ║ ║ │ │ ║ [🔒 Mutex: Solo 1 chef usa el horno a la vez] ║ │ │ ╚═══════════════════════════════════════════════════════╝ │ └─────────────────────────────────────────────────────────────┘

La sincronización:

  • Sin sincronización: Dos meseros intentan usar la misma estufa → comida quemada (race condition)
  • Con Mutex: Solo un chef cocina a la vez → ordenado pero lento
  • Con Semáforo (3 permisos): Tres chefs cocinan simultáneamente → eficiente
  • Deadlock: Chef A tiene el cuchillo y espera el tablero; Chef B tiene el tablero y espera el cuchillo

Identificar Deadlock: 3 Ejemplos

Ejemplo 1 - Orden de bloqueos incorrecto:

// Hilo A: lock(mutex1) → lock(mutex2) → unlock → unlock
// Hilo B: lock(mutex2) → lock(mutex1) → unlock → unlock
// 
// ¿Por qué causa deadlock? Los hilos bloquean en orden inverso

Ejemplo 2 - Recursión con lock no reentrante:

void funcionA() {
    lock(mutex);
    funcionB();  // Intenta adquirir el mismo mutex
    unlock(mutex);
}

void funcionB() {
    lock(mutex);  // DEADLOCK: Ya está bloqueado!
    // ...
    unlock(mutex);
}

Ejemplo 3 - Productor-Consumidor mal implementado:

// Productor: llena buffer → espera consumidor
// Consumidor: espera buffer lleno → consume
//
// Deadlock si: Productor espera señal del consumidor
//              pero el consumidor nunca fue iniciado

Pregunta: ¿Cómo evitarías cada uno de estos deadlocks?

Casos Reales: Deadlock en Producción

Caso 1: Deadlock en Recursos Compartidos

Escenario: Proceso A bloquea el recurso 1 y espera el 2. Proceso B bloquea el 2 y espera el 1.

// Proceso A
lock(mutex1);  // Bloquea recurso 1
// Espera...
lock(mutex2);  // Espera lock en recurso 2

// Proceso B  
lock(mutex2);  // Bloquea recurso 2
// Espera...
lock(mutex1);  // Espera lock en recurso 1
// ¡DEADLOCK!

Solución: Acceder a los recursos SIEMPRE en el mismo orden (1 → 2).

Caso 2: Bloqueo en Sistema de Archivos

Escenario: Un proceso de backup bloquea archivos mientras otro intenta leerlos.

Diagnóstico en Linux:

# Ver procesos bloqueados en I/O
ps aux | awk '$8=="D"'

# Ver qué archivos tiene bloqueados un proceso
lsof -p [PID]

# Matar proceso bloqueado (último recurso)
kill -9 [PID]
