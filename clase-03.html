1. El Concepto de Proceso

Un proceso es un programa en ejecución. Es la unidad de trabajo fundamental en cualquier sistema operativo moderno. Un solo programa (ej: Google Chrome) puede engendrar múltiples procesos.

1.1 Programa vs Proceso

  • Programa: Entidad pasiva, un archivo ejecutable almacenado en el disco (ej: chrome.exe).
  • Proceso: Entidad activa, con un contador de programa (PC) que indica la siguiente instrucción y un conjunto de recursos asignados.

Hilos (Threads)

Un proceso puede tener múltiples hilos de ejecución. Mientras que el proceso es el dueño de los recursos (RAM, archivos), los hilos son los ejecutores reales de las tareas en paralelo.

2. El PCB y la Estructura de Memoria

Para gestionar los procesos, el Kernel mantiene una "hoja de vida" de cada uno llamada Process Control Block (PCB).

2.1 Anatomía del PCB Profesional

CampoFunción Técnica
PIDID único del proceso para el sistema.
EstadoNuevo, Listo, Ejecución, Espera, Terminado.
PCDirección de la siguiente instrucción en RAM.
RegistrosCopia de los registros de CPU (EAX, EBX, etc.) cuando el proceso se pausa.
LímitesBase y Límite de la memoria asignada para evitar intrusiones.

2.2 El Proceso en la RAM: La "Casa" del Programa

🏠 Analogía: Imagina una Casa con 4 Habitaciones

Cuando un programa se ejecuta, el SO le asigna un espacio en la RAM (su "casa"). Esta casa tiene 4 habitaciones específicas:

📚 STACK (La Pila de Libros)

¿Qué es? Como una pila de libros donde solo puedes agregar o quitar el libro de arriba (LIFO - Last In, First Out).

¿Qué guarda?

  • Variables locales de las funciones
  • Direcciones de retorno (a dónde volver cuando termina una función)
  • Parámetros de funciones

Ejemplo práctico: Cuando llamas a una función, sus variables se apilan aquí. Al terminar, se desapilan automáticamente.

// Cada función apila sus variables:
funcionA() { int x = 10; → se guarda en STACK }
funcionB() { int y = 20; → se guarda encima en STACK }

📦 HEAP (El Almacén Flexible)

¿Qué es? Como un almacén donde puedes guardar cajas de cualquier tamaño en cualquier orden.

¿Qué guarda?

  • Memoria asignada dinámicamente durante la ejecución
  • Objetos grandes que no caben en el Stack
  • Datos que deben persistir más allá de una función

Ejemplo práctico: Cuando un programa necesita memoria "extra" mientras corre (ej: cargar un archivo grande).

// Memoria solicitada durante ejecución:
malloc(1024) // Pide 1KB en el HEAP
new Array[1000] // Objeto grande va al HEAP

⚠️ Importante: La memoria del Heap NO se libera sola. Si no la liberas, causa memory leaks (fugas de memoria).

📋 DATA (Las Variables Globales)

¿Qué es? Como un archivador con documentos importantes que siempre están disponibles.

¿Qué guarda?

  • Variables globales (visibles en todo el programa)
  • Variables estáticas (conservan su valor entre llamadas)
  • Constantes definidas en el código

Ejemplo práctico: Variables que necesitas que persistan durante toda la ejecución del programa.

// Variables que viven todo el programa:
int contadorGlobal = 0; // Se guarda en DATA
static int config = 100; // También en DATA
#define PI 3.14159 // Constante en DATA

📖 TEXT (El Libro de Instrucciones)

¿Qué es? Como el manual de instrucciones del programa. Es de solo lectura (no se puede modificar).

¿Qué guarda?

  • El código máquina (instrucciones del programa)
  • Las funciones compiladas
  • Literales de texto constantes

Ejemplo práctico: Las instrucciones que el CPU ejecuta paso a paso.

// El código compilado se guarda aquí:
void main() {
  printf("Hola"); // Las instrucciones van a TEXT
  int x = 5 + 3; // El '5+3' compilado va a TEXT
}

💡 Optimización: El SO puede compartir esta sección entre procesos idénticos (ej: varias ventanas del mismo programa).

⚠️ Caso Real: Cuando el Cambio de Contexto Mata el Rendimiento

El Incidente: Una aplicación que consume mucha memoria con 64 cores mostraba 40% de CPU de usuario pero las operaciones tardaban 10x más de lo normal.

Diagnóstico:

vmstat 1
# cs (context switches) = 150,000 por segundo

Causa Raíz:

  • La aplicación tenía un pool de procesos configurado para 1000 procesos
  • El servidor solo ejecutaba 100 operaciones concurrentes
  • 900 procesos estaban competiendo por CPU innecesariamente

Solución:

  • Reducir el pool de procesos a 150
  • Implementar un pool de procesos para manejar la multiplexación
  • Context switches bajaron a 5,000/segundo
  • Tiempo de respuesta volvió a la normalidad

Lección: Más procesos ≠ Más rendimiento. El overhead de cambio de contexto puede destruir el performance.

3. Ciclo de Vida del Proceso

Un proceso cambia de estado constantemente. El éxito de un administrador de sistemas es identificar procesos en estados anómalos.

Estados en Linux y Windows

Linux (comando ps)

  • R (Running): Ejecutando o listo para ejecutar.
  • S (Interruptible Sleep): Esperando un evento.
  • D (Uninterruptible Sleep): Esperando I/O (Disco lento).
  • Z (Zombie): Proceso muerto no recolectado por el padre.

Windows (Task Manager)

  • Running: Activo en CPU.
  • Wait: Esperando recurso o señal.
  • Suspended: Pausado por el sistema para ahorrar energía.

4. El Cambio de Contexto (Context Switch)

Es la operación mediante la cual el Kernel guarda el estado del Proceso A y carga el del Proceso B. Es lo que permite que sientas que 50 apps corren al tiempo en un solo núcleo.

El Problema del Overhead

Durante un cambio de contexto, el procesador no hace nada útil para el usuario. Es puro gasto administrativo. Si tienes demasiados procesos (thrashing), el servidor se bloquea. Esto se mide en Linux con vmstat 1 (columna cs).

5. Planificación de CPU (Scheduling)

El Scheduler es el algoritmo que decide quién entra a la CPU. En la vida real, los sistemas operativos usan Prioridades Dinámicas.

5.1 Algoritmos Clásicos vs Vida Real

  • FCFS (First-Come, First-Served): El primero que llega se atiende. Simple pero ineficiente (Efecto Convoy).
  • Round Robin (RR): Cada proceso recibe un "Quantum" de tiempo (ej: 10ms). Es el estándar para sistemas interactivos.
  • Multi-Level Feedback Queues: Estándar de Windows y Linux. Los procesos que interactúan con el usuario (Word, Chrome) suben de prioridad.

6. Laboratorio Híbrido: Comandos de Procesos

Tarea 1: Forense en Linux (Nodo Ubuntu)

# 1. Ver los 5 procesos que más RAM consumen
ps aux --sort=-%mem | head -n 6

# 2. Ver la jerarquía de procesos (quién engendró a quién)
pstree -p | head -n 10

# 3. Ver los hilos individuales de un proceso (ej: sshd)
ps -eLf | grep sshd

# 4. Ver el PCB real en texto plano
cat /proc/self/status

Tarea 2: Forense en Windows (Host/Server)

# 1. Listar procesos por uso de CPU en PowerShell
Get-Process | Sort-Object CPU -Descending | Select-Object -First 10

# 2. Ver hilos de un proceso específico
(Get-Process chrome)[0].Threads.Count

# 3. Identificar el dueño de un proceso
Get-Process -IncludeUserName | Select-Object Name, UserName -First 10

Tarea 3: El reto del Context Switch

  1. En Windows, abra Resource Monitor (resmon) → Pestaña CPU. Observe la columna "Threads".
  2. En Linux, ejecute vmstat 1 10. Anote el número de la columna cs.
  3. Abra 30 pestañas en su navegador rápidamente. ¿A cuánto subió el valor de cs?

Casos Reales del Mundo Laboral

Estos escenarios están basados en problemas reales que enfrentan los administradores de sistemas en producción.

Caso 1: El Servidor "Lento" (High Context Switching)

Escenario: Una aplicación intensiva en memoria muestra 50% de uso de CPU pero las aplicaciones que la consultan responden extremadamene lento. Al revisar con vmstat 1 observas 15,000 cambios de contexto por segundo.

Tu análisis como administrador:

  1. ¿Qué indica una tasa alta de context switch combinada con CPU baja?
  2. ¿Cómo verificarías si hay demasiados procesos pequeños competiendo por CPU?
  3. ¿Qué comando usarías para ver los procesos con más hilos?

Solución sugerida: Reducir el número de procesos concurrentes usando un pool de procesos o aumentar el valor de "nice" para procesos batch.

Caso 2: El Proceso Zombie que No Muere

Escenario: Al ejecutar ps aux ves un proceso con estado Z (Zombie) que tiene un PID específico. El proceso padre sigue activo.

Tu análisis como administrador:

  1. ¿Qué es un proceso zombie y por qué se produce?
  2. ¿Por qué no puedes matar un proceso zombie con kill -9?
  3. ¿Cómo encontrarías el proceso padre del zombie?

Solución sugerida: Matar el proceso padre con kill -CHLD [PPID] o reiniciar el servicio padre.

Caso 3: Prioridad Invertida en Producción

Escenario: Un backup automático (tar) está consumiendo 100% de un núcleo de CPU mientras tu aplicación web responde en 10 segundos cuando normalmente responde en 200ms.

Tu análisis como administrador:

  1. ¿Por qué el proceso de backup tiene tanta prioridad?
  2. ¿Cómo bajerías su prioridad sin detener el backup?
  3. ¿Qué comando usarías para un proceso que ya está corriendo?

Solución sugerida: Usar renice +19 -p [PID] para minimizar su prioridad CPU.

🛠️ Práctica Laboral

👨‍🍳 Analogía Visual: El Chef y sus Recetas

Imagina un restaurante para entender el cambio de contexto:

El Chef (CPU) solo puede preparar un plato a la vez.

Cada Receta (Proceso) tiene sus ingredientes (datos) y pasos (instrucciones) guardados en su propia estación.

Cambio de Contexto: Cuando el Chef cambia de receta, debe:

  1. Guardar el progreso de la receta actual (guardar registros)
  2. Limpiar su mesa de trabajo (flush caché)
  3. Traer los ingredientes de la nueva receta (cargar PCB)
  4. Empezar a cocinar (ejecutar nuevo proceso)

Overhead: El tiempo que el Chef gasta cambiando entre recetas NO es tiempo de cocina productivo. Si tiene que cambiar cada 5 segundos, ¡cocinará muy poco!

📊 Ejercicio Práctico: Medir Overhead con vmstat

Sigue este paso a paso para medir el overhead de cambio de contexto en tu sistema:

Paso 1: Abre una terminal y ejecuta:

vmstat 1 10

Esto muestra estadísticas cada 1 segundo, 10 veces. Mira la columna "cs" (context switches).

Paso 2: En otra terminal, genera carga:

for i in {1..1000}; do echo $i; done &

Esto crea procesos intensivos en cambios de contexto.

Paso 3: Observa cómo cambia el valor de "cs":

  • cs < 1000: Sistema saludable, bajo overhead
  • cs 1000-5000: Carga normal, aceptable
  • cs > 10000: Alto overhead, posible thrashing

Paso 4: Calcula el overhead:

# Mira el tiempo de CPU usado por el kernel vs usuario
vmstat 1 5 | tail -n 1
# Columnas: us (usuario), sy (sistema), id (idle)

Si sy (system) > 20%, el kernel está ocupado en cambios de contexto.

⚠️ Caso Real: Cuando el Cambio de Contexto Mata el Rendimiento

El Incidente: Un servidor de base de datos PostgreSQL con 64 cores mostraba 40% de CPU de usuario pero los queries tardaban 10x más de lo normal.

Diagnóstico:

vmstat 1
# cs (context switches) = 150,000 por segundo

Causa Raíz:

  • La aplicación tenía un pool de conexiones configurado para 1000 conexiones
  • El servidor solo ejecutaba 100 queries concurrentes
  • 900 procesos estaban competiendo por CPU innecesariamente

Solución:

  • Reducir el pool de conexiones a 150
  • Implementar pgBouncer para manejar la multiplexación
  • Context switches bajaron a 5,000/segundo
  • Tiempo de respuesta volvió a la normalidad

Lección: Más procesos ≠ Más rendimiento. El overhead de cambio de contexto puede destruir el performance.

🔄 Diagrama: Estados de un Proceso con Transiciones Visuales

    ┌─────────────┐
    │   NUEVO     │  ← fork() crea el proceso
    └──────┬──────┘
           │ admitido
           ▼
    ┌─────────────┐     ┌─────────────┐
    │   LISTO     │←────│  EJECUCIÓN  │  ← CPU ejecutando
    │  (Ready)    │     │  (Running)  │     instrucciones
    └──────┬──────┘     └──────┬──────┘
           │                   │
   despacho│                   │interrupción
   (CPU    │                   │(quantum
   libre)  │                   │ expirado)
           │                   │
           └─────────┬─────────┘
                     │
         I/O iniciada│
                     ▼
              ┌─────────────┐
              │  BLOQUEADO  │  ← Esperando I/O
              │   (Wait)    │     (disco, red,
              └──────┬──────┘     usuario)
                     │
         I/O         │
         completada  │
                     ▼
              ┌─────────────┐
              │  TERMINADO  │  ← exit() llamado
              │   (Zombie)  │     o kill recibido
              └─────────────┘

Transiciones clave:

  • NUEVO → LISTO: El SO asigna PCB y recursos
  • LISTO → EJECUCIÓN: El scheduler selecciona el proceso
  • EJECUCIÓN → BLOQUEADO: El proceso solicita I/O
  • BLOQUEADO → LISTO: La I/O se completa
  • EJECUCIÓN → LISTO: El quantum expira (Round Robin)
  • EJECUCIÓN → TERMINADO: El proceso finaliza
